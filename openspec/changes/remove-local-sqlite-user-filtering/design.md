# Design: Remove Local SQLite User Filtering

## Context

AChat uses a dual-DB architecture: 10 "local" tables in SQLite (agents, conversations, messages, artifacts, workspaces, etc.) and 12 "remote" tables in PostgreSQL (users, user_settings, documents, rag_chunks, etc.). The project is deployed as a local app — one person, one machine, one user. There is no server deployment mode.

Despite this, local SQLite tables inherited `user_id` columns and filtering from the multi-user PG model. The `user_id` is a nanoid generated by PG at registration time. When PG is reset (Docker volume cleared, DB recreated), the same email gets a new nanoid, and all SQLite data tagged with the old nanoid becomes invisible — queries like `WHERE user_id = <current_user>` return empty results.

Current state of affected code:
- `backend/app/auth/ownership.py` — 4 functions verify local-table ownership via `user_id`
- `backend/app/api/agents.py` — `WHERE user_id IS NULL OR user_id = ?`
- `backend/app/api/model_profiles.py` — `WHERE user_id = ?` on all CRUD
- `backend/app/services/conversation_service.py` — `WHERE user_id = ?`
- `backend/app/services/agent_runner.py` — `ModelProfile.user_id == agent.user_id`, `_resolve_model_profile` filters by `user_id`
- `backend/app/tools/manage_agents.py`, `manage_mcp.py` — `WHERE user_id = ?`
- `backend/app/db/engine.py` — migration statements that ADD COLUMN user_id on local tables
- `backend/scripts/migrate_to_multi_user.py` — back-fills `user_id` on local tables

## Goals / Non-Goals

**Goals:**
- Remove `user_id` columns and filtering from all 10 local SQLite tables
- Eliminate the PG-reset data-loss vector entirely
- Simplify local-table queries (no user_id parameter threading)
- Keep remote (PG) table isolation fully intact

**Non-Goals:**
- Removing authentication (JWT login still required for API access)
- Changing remote-table user isolation (users, user_settings, documents, RAG, memory)
- Supporting a server/multi-user deployment mode
- Changing the frontend API contract (response shapes stay the same)

## Decisions

### Decision 1: Drop `user_id` columns from local tables entirely

**Choice**: Remove the columns, not just the filtering.

**Alternatives considered**:
- *Keep columns, just stop filtering*: Simpler code change, but leaves dead columns that imply multi-user semantics they don't deliver. Confusing for future developers. Migration statements stay in engine.py for no reason.
- *Keep columns, auto-backfill at startup*: Adds startup complexity for a problem that shouldn't exist. The column has no purpose if we backfill it to a single value every time.

**Rationale**: The column serves no purpose in single-user mode. Dropping it is the clean break — no migration statements, no filtering, no ownership checks, no confusion.

### Decision 2: Replace `agent.user_id` with a single default-user lookup for ModelProfile resolution

**Choice**: `ModelProfile` queries become unfiltered (return all profiles). The "default profile" is simply `is_default = True` with no user scoping. `_resolve_model_profile` drops the `user_id` parameter.

**Rationale**: With only one user, `WHERE user_id = ? AND is_default = True` is equivalent to `WHERE is_default = True`. The `is_default` unique index changes from `(user_id) WHERE is_default = true` to a simple `WHERE is_default = true` (only one default allowed).

### Decision 3: Simplify `auth/ownership.py` — keep existence checks, drop `user_id` checks

**Choice**: Ownership verification functions for local tables become existence checks only (404 if not found, no 403). `verify_document_ownership` (remote table) is unchanged.

**Rationale**: Authentication still ensures only logged-in users can call APIs. Existence checks prevent 500 errors on missing rows. The `user_id` comparison is meaningless in single-user mode.

### Decision 4: Remove local-table `user_id` migration statements from `engine.py`

**Choice**: Remove all `ALTER TABLE ... ADD COLUMN user_id` statements for local tables from `_PG_MIGRATION_STATEMENTS` and `_SQLITE_MIGRATION_STATEMENTS`. Add `ALTER TABLE ... DROP COLUMN user_id` statements for local tables.

**Rationale**: The columns are being removed. Existing migration statements that add them are dead code. A one-time DROP COLUMN migration cleans up existing databases.

### Decision 5: Keep `user_id` on `mcp_servers` local table but stop filtering

**Choice**: Same as other local tables — drop the column entirely.

**Rationale**: `mcp_servers` is in `LOCAL_TABLES`. Same logic applies.

## Risks / Trade-offs

- **[Risk] Existing SQLite databases have `user_id` columns with data** → Migration script runs `ALTER TABLE ... DROP COLUMN` (SQLite 3.35.0+ supports this) on startup, wrapped in `suppress(Exception)` for safety. No data loss — the column is being removed, not the rows.

- **[Risk] `migrate_to_multi_user.py` script references local-table `user_id`** → Script is updated to only back-fill remote tables (documents, rag_chunks, etc.). Local-table back-fill code is removed.

- **[Risk] Code paths that pass `user_id` to local-table functions will break** → All call sites must be updated. The compiler/type checker will catch missing parameters since function signatures change.

- **[Trade-off] If server mode is ever needed in the future, user isolation for local tables would need to be re-added** → Accepted. The project has explicitly committed to dual-DB-only mode. Re-adding is straightforward (re-add column + filter).

## Migration Plan

1. **Code changes** (all in one commit): Remove `user_id` from local-table models, queries, ownership checks, and migration statements
2. **Startup migration** (in `engine.py`): Add `ALTER TABLE ... DROP COLUMN user_id` for all local tables, wrapped in `suppress(Exception)` (idempotent — fails silently if column already gone)
3. **Script update**: Update `migrate_to_multi_user.py` to only handle remote-table back-fill
4. **No data loss**: Rows are preserved; only the `user_id` column is dropped

**Rollback**: Revert the commit. The `ALTER TABLE ... ADD COLUMN user_id` migration statements (which we removed) would need to be re-added to restore the column. Data in the column would be lost (all NULL), but that's acceptable since the column had no real purpose.
