## 1. 问题背景

清单 §2 盘点的核心发现：compact_pipeline 与 prompt_assembler 的裁剪**全部按比例/位置/长度决策，不看内容相关性**——

- 掩码选择 = 工具名白名单一刀切 + 「掩码标记比原文短才换」（`compact_pipeline.py:1130-1164`），信息价值不在考虑内；
- bash 输出只留末 20 行（`:455`），中部埋藏的编译错误必然丢失；
- code_explore 无条件全文保留（`:503-507`），多次探索累积可占上下文大头；
- prompt_assembler 的 `ContextItem.score` 字段存在但预算裁剪无视它（`prompt_assembler.py:674-691`）。

mu 项目（黑客松冠军）的对应设计是「上下文只放这一步需要的：逐块判断」。Jev（~200ms、输入 $0.042/MTok、输出免费、一次调用并行回答 N 个类型化问题）首次让「循环内逐块语义判定」在延迟与成本上可行——现状管线注释明言因延迟约束刻意不用 LLM（`agent_runner.py:817`），这个前提正被 Jev 攻击。

## 2. 对象界定：两台机器，本文只设计一台

```
        一次 run 的上下文生命周期

  run 启动时（一次性）           循环内（事件驱动，阻塞下一次模型调用）
┌──────────────────────┐     ┌───────────────────────────────────┐
│ B: prompt_assembler  │     │ A: compact_pipeline                │
│ 富化上下文组装，失败   │     │ ratio ≥0.75 → stage1 掩码          │
│ 静默降级（软失败）     │     │ ratio ≥0.88 → stage3 折叠          │
│                      │     │ messages = run_compact_pipeline(…) │
│                      │     │ 原地替换，run 内不可逆（硬失败面）    │
└──────────────────────┘     └───────────────────────────────────┘
```

- **本文设计 A 的 stage 1 掩码选择**（D1-D8）。stage 3 折叠机制原样保留，ratio 触发阈值原样保留（安全网）。
- **B 机器（2.12/2.13/2.16）是低风险平行增量**：`ContextItem.score` 补齐打分来源 + `_trim_by_budget` 按分裁剪 + 死配置修复。改动面小、失败软，建议独立小 change 先行，不与本设计捆绑。
- stage 3 的用户消息保全（清单 2.9「含约束吗」模板）是本设计的自然扩展，**首期不做**（见 §8）。

## 3. 已确认的设计决策

### D1 ✅ 判决者：全 Jev，不引入向量层

压缩路径内不引入 embedding 相似度预筛。理由：Jev 一次调用并行问完所有块（~200ms），引入向量基建（Milvus/SQLite 向量索引）到压缩路径的复杂度不成比例；且「相似 ≠ 有用」——已消费的块照样语义高分，embedding 分不清消费状态。探索中曾考虑「embedding 粗筛 + Jev 裁灰区」阶梯，确认放弃。

### D2 ✅ 判定参考物：run state card，目标来源按 run 归属

相关性相对于一张约 1-2k tokens 的合成状态卡而言，而非原始「最近几轮」（最近几轮本就在 keep-recent 窗口内受保护，喂给裁判是冗余）：

```
┌─ run state card（~1-2k tokens）─────────────────────┐
│ ① 任务目标（<1k）                                   │
│    → 回答「约束类」：这条块和目标还挂钩吗              │
│ ② 剩余方向（~0.5k）：未完成计划步骤 / 最近 assistant  │
│    文本要点                                          │
│    → 回答「方向类」：对接下来要做的事还有用吗           │
│ ③ 副作用清单（~0.5k）：已写入文件路径 + 已跑关键命令   │
│    （agent_runner evidence.file_writes 现成，:2385）  │
│    → 回答「消费类」：fs_read 了 X 后来又写了 X          │
│      ⇒ 那次读取八成消费完毕                          │
└─────────────────────────────────────────────────────┘
```

**目标来源规则（按 run 归属，已确认）**：

```
goal = args.override_prompt（task_dispatch / dispatch_plan / ask_peer mini-run）
        ↓ 为空时
       当前触发消息（顶层会话 run 的 user prompt）
```

三个已确认推论：
- **ask_peer mini-run 自动覆盖**：其 `override_prompt` 是问题本身（`ask_peer.py:226`），以问题为参考物判定 peer 历史正是想要的语义，无需特例；
- **兄弟节点不共享参考物**：DAG 各 agent 对着自己的 `task_description` 判自己的上下文；上游注入结果老化后由下游目标判去留（「对我还有用吗」），state card 保持 per-run 本地；
- **历史中的旧用户消息永远只是判定对象**（走约束模板），不进 state card，参考物不随历史膨胀。

### D3 ✅ 判定对象：从「块相不相关」反转为「摘要够不够」

清单原问法「这条旧工具结果对当前任务仍有引用价值吗」需要看原文（放不进 32k，且大块预览本身丢信息——递归困境）。翻转为：

> **「这份摘要，作为原文的替代品，对剩余工作够用吗？」**

判定输入 = 候选摘要本身（tail-20 行等，本来就小）+ recover 配方 + 结构标志。原文多大无关紧要。关键事实依据：每个 summarizer 已返回 `(new_content, summary, recover)` 三件套，`recover` 是现成的重新获取配方（`compact_pipeline.py:446` `bash(command=...) 重新执行`、`:479` `fs_grep(pattern=..., path=...) 重新搜索`）。

**预算算术**（40 块典型规模）：40 × ~1k 字符摘要 ≈ 10k tokens + state card 1.5k + 问题文本 ≈ 12-15k ≪ 32k ✓ 一次调用装得下。

该问法同时取代了「only-if-shorter」长度规则（`:1163`）想回答的问题：长度规则问「换亏了吗」（字符数），新问题问「换值吗」（信息）。

### D4 ✅ 单调性红线：veto-only，无复活

代码事实：`agent_runner.py:898` 的 `messages` 是整个 run 的内存工作副本，`:1034` 原地替换——一旦掩码，原文在本 run 后续所有轮次不可见（DB 有原文，但 run 内无工具读自身历史）。

**红线：Jev 只能在掩码前否决（keep），不能复活已掩码内容。** 单调性保住 `decide_pre_model` 的 anti-oscillation 语义。推论：判定不稳定（同块两次判定结果不同）只会导致「保留得比必要更久」，无害。

### D5 🔶 bash 埋雷：保守门（默认采纳）

D3 的翻转救不了「摘要看起来干净、中部埋雷」的场景——tail-20 行判不出中部编译错误。采取**保守路线**：error 正则（error/failed/Exception/Traceback 等，具体模式实现期定）命中 → 该块**跳过掩码资格**，不进 Jev 判定，直接保留原文。

- 正则不判相关性，只判「有没有雷」；雷区的默认动作是不动。
- 放弃的激进路线（提取命中区段 ± 上下文进摘要再判富化版）留作后续优化，多错杀的 token 由 D6 地板兜住。
- exit_code 已有现成解析（`:450-452`），可并入结构标志。

### D6 🔶 压力兜底：ratio 规则降级为地板（默认采纳）

D7 的 keep 偏置可能把压缩顶死（全保 → ratio 不降 → 反复触发）。因此现行 ratio 规则**不被替换，降级为地板**：

- Jev 做减法（比规则少删），规则做地板（保证一定瘦得下来）；
- 误删率严格下降、压缩有效性有下界，两个保证互不侵犯；
- stage 3 折叠语义原样保留（spec 契约不破），Jev 只活在 stage 1 掩码选择里。

### D7 🔶 错误偏置：偏向 keep（默认采纳）

错误不对称：误留 = 浪费 token（无害）；误删 = 模型要么按 recover 配方重取（一次工具调用的代价），要么幻觉（危险）。判定阈值偏向 keep，赢面在明显大头（code_explore 囤积、被白名单误保的过期块、埋雷误保），不在抠边角料。

### D8 🔶 豁免收缩（默认采纳）

现行工具名白名单（`_is_whitelisted`，`compact_pipeline.py:1130-1134`：code_explore 全保、fs_read outline/head 全保）是 2.1 指认的问题源头。新设计中：

- **无条件豁免收缩为**：system prompt（现状已保，`:1224-1230`）、pinned 消息；
- code_explore、fs_read outline 等**原豁免块改走专用问题模板进判定**（explore 是缓存性质——可重取，不是不可恢复）；
- 白名单语义保留为「判定输入的默认倾向」而非「免死金牌」（实现期定具体形式）。

## 4. 整合后的触发流程

```
ratio ≥ 0.75 触发（decide_pre_model，触发位置与阈值不变）
   │
   ▼
┌─ 预处理（确定性，无模型）────────────────────────────┐
│ 候选集 = keep-recent 窗口外的工具结果块                │
│ system / pinned 照旧豁免（D8 收缩后仅此两类）          │
│ bash 块：error 正则扫描，命中 → 直接豁免（D5）         │
│ 每块备好判定输入：候选摘要 + recover 配方 + 结构标志    │
│   （tool 名、args_digest、turn_distance、             │
│     exit_code / 匹配数 / error_hits / 原文长度）      │
└──────────────┬──────────────────────────────────────┘
               ▼
┌─ Jev 判定（一次调用，N 个问题并行）───────────────────┐
│ 输入：state card（D2）+ 全部块的判定输入（D3）          │
│ 问题按块类型分模板（§5）                                │
│ 输出：每块 Noul（是否足以替代）+ 校准概率               │
└──────────────┬──────────────────────────────────────┘
               ▼
┌─ 应用（veto-only，D4）───────────────────────────────┐
│ 「摘要不足」或低置信 → 保留原文（本轮不掩，D7）          │
│ 「摘要足够」→ 掩码（现行 marker + 摘要格式不变）         │
└──────────────┬──────────────────────────────────────┘
               ▼
      压缩后 token 仍 ≥ 地板线（如 0.80，实现期定）？
               │ 是
               ▼
   现行无条件 ratio 规则兜底（D6）：对最老的超额块
   按现行白名单外顺序直接掩码，保证压缩有下界
```

## 5. 判定契约草案（实现期细化）

**state card 输入骨架**（JSON，Jev 原生吃结构化输入）：

```json
{
  "goal": "<override_prompt 或当前触发消息>",
  "remaining_direction": "<未完成计划步骤 / 最近 assistant 要点>",
  "side_effects": {
    "files_written": ["src/foo.py"],
    "commands_run": ["pytest -q"]
  }
}
```

**单块判定输入骨架**：

```json
{
  "block_id": "msg_123_tr_456",
  "tool": "bash",
  "args_digest": {"command": "pytest -q"},
  "turn_distance": 7,
  "candidate_digest": "exit 0\n<tail-20-lines>",
  "recover_recipe": "bash(command='pytest -q') 重新执行",
  "flags": {"exit_code": 0, "error_regex_hits": 0, "original_chars": 5231}
}
```

**问题模板（3 类，方向已圈，措辞与一致性评测 ⏳）**：

| 块类型 | 时间性质 | 模板方向 |
|---|---|---|
| 工具结果（bash/grep/fs_read/web_search/未知工具） | 消耗品 | 「以剩余工作为参照，这份摘要作为原文替代是否够用？」 |
| explore 摘要（原 code_explore 豁免块） | 缓存（可重取） | 「这份探索摘要在剩余工作中还会被引用吗？」 |
| 用户消息（stage 3 扩展，首期不做） | 约束（整个 run 有效） | 「这条消息包含的约束/需求，任务完成前还需要吗？」 |

ask_user 回答（清单 2.8）默认倾向**整块保留**（决策性内容不可重取），不进「摘要够不够」判断，或以最高 keep 偏置单独模板——实现期定。

## 6. 边界与诚实的限制

1. **误删是永久性的**。单调红线意味着 trigger 1 判错的块，trigger 2 状态卡再准也救不回（重判只对幸存块有效）。本设计承诺的是**严格少于现状的误删**（现状零语义判断），不是零误删。最终兜底是 recover 配方：模型按配方重取，代价一次工具调用。
2. **裁判只看摘要**（D5 豁免块除外）。摘要没呈现的信息对裁判不存在——这是 D3 翻转的固有代价，D5 保守门是主要补偿。
3. **state card 无法预判未显现的需求**。模型在第 20 轮才意识到需要第 3 轮读过的 schema，而第 3 轮时状态卡没有任何迹象。缓解：keep 偏置 + 每次触发对幸存块重判。
4. **非确定性**。Jev 是概率模型，压缩行为不再逐字节确定。测试需可注入的 mock 判定客户端（项目已有 MockAdapter 先例）；判定输入本身是 run 状态的确定性函数，保证可复现测试。
