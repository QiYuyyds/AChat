## 1. 系统总览

AChat 记忆系统采用 **file-native** 架构：记忆内容以 Markdown 文件 + YAML frontmatter + wikilinks 存储，用户可直接查看/编辑/版本化，不依赖外部数据库存储记忆正文。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        MemoryService (Facade)                           │
│                     memory_service.py — 统一编排入口                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ┌─────────────────── 三级文件生命周期 ─────────────────────────────┐  │
│  │                                                                 │  │
│  │   session/          daily/              digest/                 │  │
│  │   <conv>.jsonl   →   <date>/<name>.md  →   procedure/           │  │
│  │   (原始对话)          (LLM提取事实)          personal/            │  │
│  │                       (Markdown卡片)          wiki/              │  │
│  │                            ↑                       ↑             │  │
│  │                       auto_memory            auto_dream          │  │
│  │                       (每轮对话后)          (阈值触发精炼)        │  │
│  └─────────────────────────────────────────────────────────────────┘  │
│                                                                         │
│  ┌─────────────────── 混合检索 (HybridSearch) ──────────────────────┐  │
│  │                                                                 │  │
│  │   query ──┬── BM25 (SQLite FTS5) ──────┐                       │  │
│  │           │                              ├─ RRF 融合 → top-k    │  │
│  │           └── Vector (SQLite BLOB) ─────┘                       │  │
│  │                  (brute-force cosine)                             │  │
│  │                                                                    │  │
│  │   → Rerank: importance_factor × decay × recency 重排序                   │  │
│  │   → Daily TTL 过滤: 过期且已蒸馏的 daily 卡片排除                  │  │
│  │   → archived 节点 BM25 降权 0.5x                                  │  │
│  │   → wikilink 扩展: 惰性构建 outlinks/inlinks 邻居元数据            │  │
│  └─────────────────────────────────────────────────────────────────┘  │
│                                                                         │
│  ┌─────────────────── Preference (PG KV) ──────────────────────────┐  │
│  │  用户偏好键值对 — user_preferences 表                            │  │
│  │  LLM 提取 + 规则兜底 + 同义词归一                                 │  │
│  └─────────────────────────────────────────────────────────────────┘  │
│                                                                         │
│  ┌─────────────────── Proactive (主动话题) ────────────────────────┐  │
│  │  daily/<date>/interests.yaml → 注入 Agent system prompt          │  │
│  └─────────────────────────────────────────────────────────────────┘  │
│                                                                         │
│  ┌─────────────────── Curator (夜间治理) ─────────────────────────┐  │
│  │  auto_dream_cron 定时触发四步管线:                              │  │
│  │  1. auto_dream (增量)  2. daily governance                       │  │
│  │  3. digest governance (归档低分卡片)  4. full reindex            │  │
│  └─────────────────────────────────────────────────────────────────┘  │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘

                    ┌─── metadata/ (SQLite 索引层) ─────────┐
                    │  bm25.db         — FTS5 全文索引      │
                    │  wikilinks.db    — 邻接图 (predicate)  │
                    │  catalog.db      — 文件变更追踪        │
                    │  vectors.db      — 向量 BLOB 存储      │
                    │  access_stats.db — 访问统计 + 水印      │
                    └──────────────────────────────────────┘
```

### 设计原则

- **file-native**：记忆内容是 Markdown 文件，不是数据库里的行
- **三级生命周期**：session（原始对话）→ daily（LLM 提取事实）→ digest（精炼长期记忆）
- **混合检索**：BM25 关键词 + Vector 向量语义，RRF 融合
- **可降级**：缺少 embedding 函数时退化为纯 BM25；缺少 LLM 时 auto_memory/auto_dream 跳过
- **搜索质量优化**：Rerank 重排序（importance_factor × decay × recency）+ Daily TTL 过滤 + AccessStats 访问统计
- **生命周期治理**：Curator 夜间定时执行 auto_dream + 过期卡片日志 + 低分卡片归档 + 全量重建索引
- **用户可干预**：所有记忆文件可通过 API/UI 查看、编辑、删除、移动

## 3. 文件存储层 (file_store/)

### 3.1 MemoryWorkspace — 工作区目录管理

**文件**：`file_store/workspace.py`

管理三级生命周期目录树的创建和路径解析。

```python
class MemoryWorkspace:
    def __init__(self, settings: Settings):
        self.root: Path = settings.memory_workspace_path
        self.session_dir: Path = self.root / "session"
        self.daily_dir: Path = self.root / "daily"
        self.digest_dir: Path = self.root / "digest"
        self.metadata_dir: Path = self.root / "metadata"
```

**关键方法**：

| 方法                                    | 说明                                                                                                                        |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `initialize()`                        | 创建完整目录树（含 digest 子目录 procedure/shared, procedure/agents, personal, wiki）                                                  |
| `session_path(conv_id)`               | 返回 `session/<conv_id>.jsonl` 路径                                                                                           |
| `daily_dir_for_date(day)`             | 返回 `daily/<YYYY-MM-DD>/` 目录（自动创建）                                                                                         |
| `daily_file_path(name, day)`          | 返回 `daily/<YYYY-MM-DD>/<name>.md` 路径                                                                                      |
| `interests_path(day)`                 | 返回 `daily/<YYYY-MM-DD>/interests.yaml` 路径                                                                                 |
| `digest_path(bucket, name, agent_id)` | 根据 bucket 和 agent_id 返回 digest 文件路径（procedure + agent_id → agents/<id>/，procedure 无 agent_id → shared/，wiki → 直接 wiki/ 下） |
| `list_digest_files(bucket, agent_id)` | 列出 digest 文件，支持按 bucket/agent 过滤                                                                                          |
| `list_daily_files(day)`               | 列出指定日期（或全部）的 daily 卡片                                                                                                     |
| `count_unprocessed_daily_cards()`     | 统计 daily/ 下 .md 文件数（用于 auto_dream 阈值触发）                                                                                   |

### 3.2 MemoryFrontmatter — YAML Frontmatter Schema

**文件**：`file_store/frontmatter.py`

每个记忆 Markdown 文件的 frontmatter 包含以下字段：

```yaml
---
name: "记忆标题"
description: "一行摘要"
agent_id: null           # 关联的 Agent ID（全局记忆为 null）
tags: ["tag1", "tag2"]    # 检索标签（最多 10 个）
importance: 0.5           # 重要性 0.0-1.0
bucket: "wiki"            # procedure | personal | wiki
status: "active"          # active | archived | superseded
created_at: "2026-08-05"  # YYYY-MM-DD
updated_at: "2026-08-05"  # YYYY-MM-DD
source: "session/conv123.jsonl"  # 来源路径
stable_key: "wiki.topic.name"    # 合并键（跨标题变体去重）
---
```

**验证规则**：
- `name` 必填
- `bucket` 必须是 `procedure` / `personal` / `wiki` 之一
- `status` 必须是 `active` / `archived` / `superseded` 之一（`superseded` 表示用户显式变更状态后重写的卡片，旧事实不保留）
- `importance` 必须在 0.0-1.0 范围内
- `stable_key` 为空时自动从 `bucket` + `name` 生成

### 3.4 wikilinks — Wikilink 解析与渲染

**文件**：`file_store/wikilinks.py`

 **wikilinks** 指的是一种“笔记内部链接”语法，中文常叫 **维基链接**。它用双方括号 `[[...]]` 把一个笔记或文件链接起来。
 在你这份文档里，相关例子是：

```markdown
[[digest/wiki/react-19.md]]
```

它表示链接到 `digest/wiki/react-19.md` 这个文件。点击后可以直接打开对应笔记。

支持三种 wikilink 语法：

| 语法 | 说明 | 示例 |
|------|------|------|
| `[[target]]` | 普通 wikilink | `[[digest/wiki/react-19.md]]` |
| `[[target\|alias]]` | 带别名 | `[[daily/2026-08-05/card.md\|原始卡片]]` |
| `predicate:: [[target]]` | 带谓词 | `derived_from:: [[daily/2026-08-05/card.md]]` |

**谓词词表**（约定，非强制）：

| 谓词 | 语义 | 使用场景 |
|------|------|---------|
| `derived_from` | 源自 | digest 节点指向 daily 卡片（provenance） |
| `relates_to` | 相关于 | 跨 bucket 关联（如 personal → wiki） |

```markdown
derived_from:: [[daily/2026-08-05/card.md]]
```

这里：

- `derived_from` 是谓词，表示“来源于”
- `::` 是谓词和内容之间的分隔符
- `[[daily/2026-08-05/card.md]]` 是具体链接

整体可以理解成：

> 当前内容来源于 `daily/2026-08-05/card.md`

**关键函数**：

| 函数 | 说明 |
|------|------|
| `extract_wikilinks(body)` | 提取所有 target（去重保序） |
| `extract_wikilinks_detailed(body)` | 提取 `list[WikilinkLink]`（含 predicate + alias） |
| `render_wikilinks(body)` | 渲染为 Markdown 链接（用于显示） |
| `add_wikilink(body, target, predicate)` | 追加 wikilink（已存在则不重复） |
| `retarget_wikilinks(body, old, new)` | 将 body 中所有 `[[old]]` 替换为 `[[new]]` |

### 3.5 FileCatalog — 文件变更追踪

**文件**：`file_store/file_catalog.py`

FileCatalog 是一个基于 SQLite 的**文件变更追踪表**，记录"哪些记忆文件被修改过"。核心目的是让 `auto_dream` 精炼管线**只处理变更过的文件**，而不是每次都全量扫描所有 daily 卡片。

存储在 `metadata/catalog.db`，与其他三个索引数据库并列：

```
metadata/
├── bm25.db         — BM25 全文索引
├── wikilinks.db    — wikilink 邻接图
├── catalog.db      — ← FileCatalog，文件变更追踪
├── vectors.db      — 向量 BLOB 存储
└── access_stats.db — 访问统计 + 水印
```

**表结构**

```sql
CREATE TABLE memory_catalog (
    path TEXT PRIMARY KEY,    -- 文件相对路径
    st_mtime REAL,             -- 文件最后修改时间（mtime）
    bucket TEXT                -- 文件所属 bucket: "daily" / "procedure" / "personal" / "wiki"
);
```

核心思路：**用文件的 `mtime`（修改时间戳）来判断文件是否变过**。

#### 解决什么问题

```
┌──────────────────────────────────────────────────────────────────────┐
│                    没有 FileCatalog 会怎样？                           │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  auto_dream 的 extract 步骤需要读取所有 daily 卡片发给 LLM 精炼。      │
│                                                                      │
│  如果每次都扫描 daily/ 目录下的全部 .md 文件：                         │
│                                                                      │
│    daily/                                                            │
│    ├── 2026-08-01/                                                   │
│    │   ├── card-a.md   ← 3天前处理过了，没变                          │
│    │   └── card-b.md   ← 3天前处理过了，没变                          │
│    ├── 2026-08-02/                                                   │
│    │   └── card-c.md   ← 2天前处理过了，没变                          │
│    └── 2026-08-03/                                                   │
│        └── card-d.md   ← 刚刚新写入的！                              │
│                                                                      │
│  每次触发 auto_dream 都把 a/b/c/d 全部读一遍发给 LLM →                │
│    1. 浪费 token（a/b/c 没变，LLM 会重复提取相同内容）                 │
│    2. 浪费时间（全量扫描 vs 只读 1 个文件）                           │
│    3. LLM 重复处理 → 可能产生重复的 digest 记忆                        │
│                                                                      │
│  有了 FileCatalog 后：                                                │
│    get_changed(bucket='daily') → 只返回 card-d.md                    │
│    auto_dream 只把 card-d.md 发给 LLM → 省 token + 省时间             │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

#### 工作机制

FileCatalog 通过 **mtime 对比** 来检测变更，并使用 **mtime=0 作为 pending 标记**：

```
文件写入/更新
   │
   ├── auto_memory 写入 daily card 后
   │    → file_catalog.upsert(path, st_mtime=0.0, bucket="daily")
   │       mtime=0 是 pending 标记: “需要 dream 处理”
   │       get_changed() 和 count_changed() 对 mtime=0 总是算作“已变更”
   │
   └── auto_dream 触发时
        → file_catalog.get_changed(bucket="daily")
           遍历 catalog 表，对比每条记录的 st_mtime 和文件实际 mtime:
             ├── st_mtime == 0 (pending) → 总是算作变更 → 加入变更列表
             ├── 文件实际 mtime != 记录的 mtime → 文件被改过 → 加入变更列表
             ├── 文件实际 mtime == 记录的 mtime → 没变 → 跳过
             └── 文件不存在 → 从 catalog 中删除这条记录（自动清理）
           处理后更新 st_mtime 为文件实际 mtime
```

#### 关键方法

| 方法 | 调用时机 | 作用 |
|------|---------|------|
| `initialize()` | `MemoryService.initialize()` | 创建 SQLite 连接和表 |
| `reconcile(daily_dir, digest_dir)` | 启动时 | 全量扫描磁盘目录，与 catalog 表对账（新增文件加入、已删文件移除、mtime 更新；保留 pending 标记 mtime=0 不被覆盖） |
| `get_changed(bucket)` | `auto_dream` extract 步骤 | 返回 mtime 变化的 `(path, bucket)` 列表（同时自动清理已删除文件的记录，更新已处理文件的 mtime） |
| `count_changed(bucket)` | `auto_dream` 阈值检查 | **只读**：返回 pending + mtime 变化的文件数，不更新 mtime、不删记录。用于 `should_trigger` 安全检查 |
| `upsert(path, st_mtime, bucket)` | `auto_memory`/`auto_dream` 写入文件后 | 插入或更新文件的 mtime 记录（`st_mtime=0` 时写入 pending 标记） |
| `remove(path)` | 文件被删除时 | 从 catalog 中移除记录 |
| `count()` | 调试/日志 | 返回记录总数 |

#### 完整生命周期

```
┌─────────────── 启动时 ───────────────────────────────────┐
│                                                          │
│  MemoryService.initialize()                              │
│    └── file_catalog.reconcile(daily_dir, digest_dir)     │
│         扫描磁盘所有 .md 文件                             │
│         与 catalog 表对账:                               │
│           - 磁盘有、表没 → 新增记录                       │
│           - 表有、磁盘没 → 删除记录                       │
│           - 两边都有 → 更新 mtime                        │
│                                                          │
├─────────────── 运行时写入 ──────────────────────────────┤
│                                                          │
│  auto_memory 写入 daily card                             │
│    └── file_catalog.upsert(path, mtime, "daily")         │
│                                                          │
├─────────────── 运行时读取 ──────────────────────────────┤
│                                                          │
│  auto_dream extract                                      │
│    └── file_catalog.get_changed(bucket="daily")          │
│         → 只返回 mtime 变化的文件                         │
│         → 如果没有变更 → fallback 扫描最近 7 天的 daily/  │
│                                                          │
├─────────────── auto_dream 写入 digest ───────────────────┤
│                                                          │
│  auto_dream integrate                                   │
│    └── file_catalog.upsert(path, mtime, bucket)          │
│       digest 文件也纳入追踪                              │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

#### 不参与搜索

FileCatalog **不参与搜索**，只服务于 `auto_dream` 的增量处理。搜索走的是 BM25 + Vector + WikilinkExpander 这三套索引，和 FileCatalog 无关：

```
搜索链路:  query → BM25 + Vector → RRF → 结果
           （完全不碰 FileCatalog）

精炼链路:  auto_dream → FileCatalog.get_changed() → 只读变更文件 → LLM → digest
           （FileCatalog 是核心）
```

#### 为什么不用文件系统监听（如 watchdog）

项目是本地运行的，进程可能重启、可能休眠，文件系统监听不可靠。`FileCatalog` 用 SQLite 存 mtime 快照，**进程重启后 `reconcile()` 就能恢复一致状态**，比 watchdog 更可靠且零依赖。

## 4. 提取管线 (pipeline/)

### 4.1 auto_memory — 对话 → daily 卡片

**文件**：`pipeline/auto_memory.py`

#### 是什么

auto_memory 是记忆系统的**写入入口**。每当用户和 Agent 完成一轮对话后，auto_memory 会调用 LLM 从对话内容中提取"值得未来记住的事实"（如决策、技术选型、工作状态），写入一个 Markdown 文件（daily card）。这些 daily card 后续会被 auto_dream 精炼为长期记忆（digest）。

#### 在记忆系统中的位置

```
用户发消息 → Agent 回复 → on_message_end('assistant')
                                │
                     ┌──────────▼──────────┐
                     │     auto_memory      │  ← 本节
                     │  LLM 从对话提取事实   │
                     └──────────┬──────────┘
                                │
                     写入 daily/<date>/<name>.md
                                │
                     ┌──────────▼──────────┐
                     │     auto_index       │  → 更新 BM25/Vector/Wikilink 索引
                     └──────────┬──────────┘
                                │
                     daily pending 卡片数 ≥ 5 → 触发 auto_dream → 精炼到 digest
                                (含 cooldown 检查)
```

简单说：auto_memory 负责"记笔记"，把对话中的有价值信息写成卡片；后续 auto_dream 负责"整理笔记"，把卡片精炼成长期知识。

#### 触发时机

`MemoryService.on_message_end(role='assistant')` → 后台 task 调用 `auto_memory.run(user_msg, assistant_msg, conversation_id, agent_id)`

#### 提取规则

**提取什么**：
- 决策及其理由
- 当前工作状态（已完成/待做）
- 可复用的流程或模式
- 技术上下文（技术栈、架构决策、约束）
- 任务结果和经验教训

**不提取什么**：
- 用户个人偏好（由 Preference 系统处理）
- 寒暄、闲聊、填充语
- 无复用价值的临时细节
- 可从代码推导的信息

#### 两条路径

```
对话结束
   │
   ├── 查找现有卡片（通过 conversation_id 匹配 frontmatter.source）
   │
   ├── 存在 → _update_card（UPDATE 路径）
   │    │   prompt: 已有 body + 新对话 → 合并规则 → LLM
   │    │   合并规则:
   │    │     - 时间线事件: 追加
   │    │     - 状态描述: 重写（替换旧状态）
   │    │     - 语义重复: 跳过
   │    │   输出: 完整合并后 body
   │    │
   │    └── 如果 LLM 生成的 name 与现有不同 → 文件重命名 + wikilink retarget
   │
   └── 不存在 → _create_card（CREATE 路径）
        │   prompt: 对话 → LLM
        │   输出: {action, name, description, body, tags, importance}
        │
        └── 文件名 = sanitize(name) + hash(conversation_id)[:6]
```

#### CREATE 路径示例

假设用户和 Agent 讨论了"用 PostgreSQL 还是 SQLite"的选型问题：

**LLM 收到的 prompt（CREATE 路径）**：
```
[System] You are a Memory Extractor...
[User] ## Task
Create a new daily memory card from the following conversation.
...
## Conversation
[{"role":"user","content":"我们项目用 PostgreSQL 还是 SQLite？"},
 {"role":"assistant","content":"本地运行用 SQLite WAL 就够了，远端用 PostgreSQL..."}]
```

**LLM 返回的 JSON**：
```json
{
  "action": "create",
  "name": "database-selection-postgresql-vs-sqlite",
  "description": "项目数据库选型决策：本地 SQLite + 远端 PostgreSQL",
  "body": "## 决策\n- 本地运行用 SQLite WAL 模式\n- 远端部署用 PostgreSQL 16\n\n## 理由\n- SQLite 无需独立服务，本地开发零依赖\n- PostgreSQL 用于多用户并发场景",
  "tags": ["database", "postgresql", "sqlite", "architecture"],
  "importance": 0.8
}
```

**最终写入的文件** `daily/2026-08-25/database-selection-postgresql-vs-sqlite-a1b2c3.md`：
```yaml
---
name: "database-selection-postgresql-vs-sqlite"
description: "项目数据库选型决策：本地 SQLite + 远端 PostgreSQL"
agent_id: "agent_xxx"
tags: ["database", "postgresql", "sqlite", "architecture"]
importance: 0.8
bucket: "procedure"
status: "active"
created_at: "2026-08-25"
updated_at: "2026-08-25"
source: "session/conv_abc123.jsonl"
---

## 决策
- 本地运行用 SQLite WAL 模式
- 远端部署用 PostgreSQL 16

## 理由
- SQLite 无需独立服务，本地开发零依赖
- PostgreSQL 用于多用户并发场景
```

#### UPDATE 路径的合并规则

当同一 conversation 的后续对话到达时，auto_memory 找到已有卡片并走 UPDATE 路径。LLM 收到已有 body + 新对话，按以下规则合并：

| 内容类型 | 合并方式 | 示例 |
|---------|---------|------|
| 时间线事件 | **追加**（按时间排列在末尾） | 新增一条"切换到 PostgreSQL"的记录 |
| 状态描述 | **重写**（替换旧状态为新状态） | "当前状态：已完成选型" 替换旧的 "当前状态：选型中" |
| 语义重复 | **跳过**（不重复写入） | 新对话再次提到"用 SQLite"，已有此条 → 不写 |

如果 LLM 返回的 `name` 与现有卡片不同，文件会被重命名，同时全工作区的 wikilink 自动重定向（retarget）到新路径。

#### Trivial 检查（两层过滤）

系统在对话进入 auto_memory 之前设置了**两层**寒暄过滤，避免浪费 LLM 调用：

| 层级 | 位置 | 检查规则 | 说明 |
|------|------|---------|------|
| 第一层 | `MemoryService._is_trivial_reply(content)` | assistant 消息长度 < 10 字符，或匹配寒暄正则（"好的""没问题""OK""收到""明白"等） | 在 `on_message_end` 入口处过滤，不创建后台 task |
| 第二层 | `AutoMemory._is_trivial(user_msg, assistant_msg)` | user + assistant 合并长度 < 30 字符，或匹配寒暄正则 | 在 `auto_memory.run()` 入口处二次过滤，防止绕过第一层的短消息 |

两层都通过后才会调用 LLM 进行记忆提取。

#### Daily 卡片的 frontmatter.bucket 值

`_create_card` 创建 daily 卡片时，frontmatter 中的 `bucket` 字段硬编码为 `"procedure"`（而非 "daily"）。这是因为 daily 卡片尚处于中间态，`bucket` 字段的三个合法值（`procedure` / `personal` / `wiki`）是面向 digest 层的分类。daily 卡片最终会被 auto_dream 精炼到 digest 并获得正确的 bucket 分类，daily 阶段的 bucket 值仅作为占位。BM25 搜索时可通过 `bucket="daily"` 过滤 daily 卡片（此时匹配的是文件路径而非 frontmatter.bucket 字段）。

#### Session JSONL 双写

`write_session_jsonl(conversation_id, messages)` — 将对话消息（净化后）追加写入 `session/<conv_id>.jsonl`：
- 消息 ID 去重（已有 ID 不重复写入）
- 剥离 `tool_result` 和 `tool_use` parts
- 剥离 base64 数据块
- 超长内容截断（50KB）

### 4.2 auto_index — 索引维护

**文件**：`pipeline/auto_index.py`

#### 是什么

auto_index 是记忆系统的**索引维护器**。每当记忆文件被写入或更新时，auto_index 负责把文件内容同步到四个索引系统中，让后续的搜索（HybridSearch）能找到这条记忆。

#### 为什么需要它

记忆文件是 Markdown，存在磁盘上。但用户搜索时不能逐个打开文件全文匹配——太慢了。所以需要预先建好索引：

```
┌──────────────────────────────────────────────────────────────────────┐
│                    记忆文件 vs 索引的关系                              │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  daily/2026-08-25/card-a.md  ──┐                                    │
│  daily/2026-08-25/card-b.md  ──┤                                    │
│  digest/wiki/react-19.md     ──┼──→ auto_index ──→ 4 套索引         │
│  digest/proc/deploy.md       ──┘                   │                  │
│                                                    │                  │
│                                    ┌───────────────┼──────────────┐ │
│                                    │               │              │ │
│                                BM25 索引      Wikilink 图      Vector │ │
│                              (关键词搜索)    (邻接关系)      (语义搜索)│ │
│                                    │               │              │ │
│                                    └───────┬───────┘              │ │
│                                            │                      │ │
│                                        HybridSearch               │ │
│                                     (用户搜索时用)                 │ │
│                                                                      │
│  + FileCatalog (文件变更追踪，只服务于 auto_dream)                   │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

#### 两种工作模式

| 模式 | 触发时机 | 作用 |
|------|---------|------|
| **增量索引** `index_file(filepath)` | `auto_memory` 写入 daily card 后、`auto_dream` 写入 digest 后、`memory_store` 工具写入后 | 只索引单个文件，快速 |
| **全量重建** `full_reindex()` | `MemoryService.initialize()` 启动时、`auto_dream` 完成后 | 清空所有索引，遍历所有 .md 文件重建，慢但彻底 |

#### 索引流程

```
文件写入/更新
   │
   ├── read_markdown(filepath) → MemoryFile
   │
   ├── BM25 索引
   │    ├── index_text = name + description + _indexable_body(body)
   │    │   (_indexable_body 去掉 predicate wikilink 行，避免路径污染关键词搜索)
   │    └── bm25.add(path, name, index_text, agent_id, bucket, tags)
   │
   ├── Wikilink 图
   │    ├── expander.remove_edges_for(rel)  — 清除旧边
   │    ├── links = extract_wikilinks_detailed(body)
   │    ├── expander.add_edges_detailed(rel, [(target, predicate), ...])
   │    └── 断链检测: target 不存在时记录 debug 日志
   │
   ├── FileCatalog
   │    └── file_catalog.upsert(rel, bucket)
   │
   └── Vector 索引（当 embed_fn + vector_index + chunker 均可用时）
        ├── vector_index.remove(rel)  — 清除旧向量
        ├── chunks = chunker.chunk(mem_file)
        └── for chunk: embed_fn(chunk.text) → vector_index.add(rel, idx, text, emb, agent_id, bucket)
            (embedding 生成失败时 break 跳过该文件剩余 chunks)
```

#### 全量重建

`full_reindex()` — 启动时调用：
1. `bm25.clear()` + `expander.clear()` + `vector_index.clear()`
2. 遍历 `daily/` 和 `digest/` 下所有 .md 文件
3. 逐文件调用 `index_file()`
4. 清理断链：`expander.remove_broken_links(existing_paths)`

#### 索引内容细节

**BM25 索引文本**：BM25 是一种基于词频的全文检索算法（类似搜索引擎的关键词匹配）。索引文本由三部分拼接：

```
index_text = name + description + _indexable_body(body)
```

其中 `_indexable_body(body)` 会**过滤掉 predicate wikilink 行**（如 `derived_from:: [[daily/...]]`）。原因是这些行包含文件路径，如果放进去会污染关键词搜索——用户搜 "daily" 不是想找 wikilink 路径里含 "daily" 的文件。

**bucket 值的路径判断**：`index_file` 中，daily 卡片的 bucket 值由**文件路径**决定而非 frontmatter：

```python
# 路径在 daily/ 目录下 → bucket = "daily"（用于搜索过滤）
# 路径在 digest/ 目录下 → bucket = frontmatter.bucket（procedure/personal/wiki）
is_daily = self._is_daily_file(filepath)
bucket = "daily" if is_daily else (mem_file.frontmatter.bucket or "wiki")
```

这意味着：虽然 daily 卡片的 frontmatter.bucket 写的是 "procedure"，但 BM25 索引中它的 bucket 字段是 "daily"。搜索时 `bucket="daily"` 能过滤出所有 daily 卡片，`bucket="procedure"` 只返回 digest 里的 procedure 文件。

**Vector 索引的降级**：Vector 索引是可选的——只有当 `embed_fn`（embedding 函数）、`vector_index`、`chunker` 三个组件同时可用时才执行。如果 embedding API 未配置，auto_index 会跳过 Vector 索引，只维护 BM25 + Wikilink + FileCatalog 三套索引。搜索时 HybridSearch 会退化为纯 BM25。

### 4.3 auto_dream — daily → digest 精炼

auto_dream 是记忆系统的**精炼管线**。它把多条 daily 卡片（临时笔记）中零散的事实，通过 LLM 提炼为结构化的长期记忆（digest），并按三种 bucket（procedure / personal / wiki）分类存储。


类比人脑在睡眠时整理白天记忆的过程：白天产生大量临时记忆（daily cards），睡眠时大脑会精炼、合并、归类重要信息到长期记忆（digest）。auto_dream 就是系统的"睡眠整理"——在对话积累到一定量后自动触发，把碎片化的 daily 卡片精炼为可复用的知识。


```
daily/ (临时笔记, auto_memory 写入)          digest/ (长期记忆, auto_dream 写入)
┌──────────────────────────┐                ┌────────────────────────────────┐
│ 2026-08-25/               │                │ procedure/                      │
│   ├── db-selection-a1.md  │── auto_dream ─▶│   shared/deploy-runbook.md     │
│   ├── auth-design-b2.md   │    extract +   │ personal/                      │
│   └── bug-fix-c3.md       │    integrate   │   user-preferences.md          │
│ 2026-08-24/               │                │ wiki/                          │
│   └── api-test-d4.md      │                │   react-19-features.md          │
└──────────────────────────┘                └────────────────────────────────┘
         ↑                                            ↑
   3次 LLM 调用                               结构化 Markdown
   (extract/integrate/topics)                + frontmatter + wikilinks
```

#### 三步管线

auto_dream 由三步管线组成：extract → integrate → topics。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        auto_dream 三步管线                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Step 1: extract (提取)                                                 │
│  ──────────────────────────                                             │
│  输入: 变更的 daily 卡片 (via FileCatalog)                               │
│  动作: LLM 从多条卡片中提取可复用抽象                                    │
│  输出: units[] (分类为 procedure/personal/wiki) + topic_candidates[]     │
│  调用: 1 次 LLM                                                         │
│                                                                         │
│  Step 2: integrate (整合)  ← 对每个 unit 逐个执行                        │
│  ──────────────────────────                                             │
│  输入: 1 个 unit + 现有 digest 节点 (via NodeSearch)                     │
│  动作: LLM 决定 CREATE/CORROBORATE/REFINE/CORRECT + 程序写入            │
│  输出: 写入/更新 digest/<bucket>/<name>.md                              │
│  调用: N 次 LLM (N = units 数量)                                        │
│                                                                         │
│  Step 3: topics (话题)                                                  │
│  ──────────────────────────                                             │
│  输入: topic_candidates + 最近 7 天历史话题                              │
│  动作: LLM 选择最有价值的 ≤3 个话题                                     │
│  输出: 写入 daily/<date>/interests.yaml                                 │
│  调用: 1 次 LLM                                                         │
│                                                                         │
│  总计: 1 + N + 1 次 LLM 调用 (N 通常 ≤5)                                │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**触发机制**

- **自动触发**：`auto_memory` 写入 daily 卡片后检查 `check_auto_dream_threshold()`，当 pending daily 卡片数 ≥ `memory_auto_dream_threshold`（默认 5）时后台触发。`check_auto_dream_threshold` 使用 `count_changed`（只读，不消耗 pending 标记）检查 pending 卡片数，并检查 cooldown：距上次 dream 完成时间需 ≥ `memory_dream_cooldown_minutes`（默认 360 分钟）。
- **Curator 定时触发**：`CuratorJob` 按 `memory_auto_dream_cron`（默认 `23:00`）定时执行四步夜间管线（详见 §15）
- **手动触发**：`POST /api/memory/auto-dream` 或 `manage_memory` 工具的 `consolidate` action

#### Step 1: extract — 提取可复用抽象
**unit 的完整字段**
```
unit = {
    "name":         "Database Selection Runbook",     # LLM 生成
    "bucket":       "procedure",                        # LLM 生成 → 程序可能 rebucket
    "summary":      "本地 SQLite + 远端 PostgreSQL",    # LLM 生成
    "content":       "## Trigger\n当项目需要...",        # LLM 生成 → 程序可能截断
    "tags":          ["database", "architecture"],       # LLM 生成
    "importance":    0.8,                                # LLM 生成
    "source_paths":  ["daily/2026-08-25/card-a.md"],    # LLM 生成 → 程序验证匹配
    "stable_key":    "proc.db.selection",                # ← LLM 可能给，也可能不给.它的值不一定是 LLM 生成的。
}
```

```
_dream_extract(max_units)
│
├── 1. 收集变更文件 (FileCatalog.get_changed)
│      │
│      │  向 FileCatalog 查询: "哪些 daily 文件被修改过？"
│      │  FileCatalog 通过 mtime 对比返回变更列表

│      │
│      │  prompt = "## Daily Memory Cards\n\n" + 卡片用 "---" 分隔

│      │  }
│      │
│      └── 解析失败 → 返回 ([], [])
│
├── 4. source_paths 验证 (防 LLM 编造来源)
│      │
│      │  问题: LLM 可能在 source_paths 里写了不存在的路径,
│      │        或者拼写错误。如果不验证, 后续写入 derived_from wikilink
│      │        时会指向不存在的文件。
│      │
│      │  对每个 unit 的 source_paths:
│      │    ├── _match_changed_path(path, changed_paths)
│      │    │   三种匹配策略:
│      │    │     1. 精确匹配 (路径完全一致)
│      │    │     2. slash 归一化匹配 (Windows \ vs /)
│      │    │     3. basename 唯一匹配 (只看文件名, 且只有一个同名文件)
│      │    │
│      │    ├── 匹配成功 → 保留原始路径 (不是 LLM 的, 而是 catalog 里的真实路径)
│      │    ├── 匹配失败 → 丢弃该 path
│      │    └── 所有 path 都没匹配上 + 只有 1 个变更文件 → 自动归因到那个文件
│      │        (唯一来源兜底: 如果今天只改了 1 个 daily card,
│      │         这个 unit 只可能来自它)
│      │
│      └── 验证后 unit["source_paths"] 只含有效路径
│
├── 5. validate_and_normalize_unit() 程序门控
│      │
│      │  这是 extract 的最后一道关卡, 纯程序逻辑, 不依赖 LLM。
│      │  目的: 防止 LLM 把内容分错 bucket 或塞入不该有的内容。
│      │
│      │  检查 1: delivery/项目状态内容误标 personal
│      │    正则匹配: in_review|部署预览|功能清单|交付记录|task.complete|localStorage
│      │    如果命中 + 有 runbook 信号(## Trigger|## Steps) → rebucket 为 procedure
│      │    如果命中 + 无 runbook 信号 → 直接 drop (丢弃)
│      │
│      │  检查 2: runbook 形式误标 personal
│      │    正则匹配: ## Trigger|## Steps|按以下步骤|操作步骤
│      │    如果命中 → rebucket 为 procedure
│      │
│      │  检查 3: 百科内容误标 personal
│      │    正则匹配: 万字|章节|收藏|总推荐|代表作|K歌|必听|单曲循环|评分|完结
│      │    如果命中:
│      │      → _shorten_personal_content() 截断为短规则卡
│      │      → 截断后无用户主体信号(没有"用户""本人""我""偏好"等词)
│      │        → rebucket 为 wiki
│      │
│      │  检查 4: personal 长度
│      │    len(content) > 900 → _shorten_personal_content()
│      │
│      │  最后: make_stable_key(bucket, name, explicit)
│      │    生成稳定的合并键, 用于 integrate 步骤
│      │
│      └── 返回 None = 丢弃该 unit, 返回 dict = 保留
│
└── 6. 截断: normalized_units[:max_units]
       最多保留 5 个 unit (max_units 默认 5)
       返回: (units, topic_candidates)
```

#### Step 2: integrate — 写入 digest

对 extract 产出的每个 unit，查找 digest 目录中是否已有类似的知识节点，让 LLM 决定是新建、补充、确认还是修正，然后程序执行写入。

```
┌──────────────────────────────────────────────────────────────────────┐
│                    LLM 的五种 Action 决策                              │
├──────────────┬──────────────────┬─────────────────────────────────────┤
│ Action       │ LLM 输出         │ 程序行为                             │
├──────────────┼──────────────────┼─────────────────────────────────────┤
│ CREATE       │ 完整 body        │ 新建 digest 文件                     │
│              │                  │ (但 stable_key 命中时强制改 REFINE)  │
├──────────────┼──────────────────┼─────────────────────────────────────┤
│ CORROBORATE  │ 仅新证据/来源    │ 追加 "## Update (date)" 段落          │
│              │ (确认已有内容)    │ ≥3 次时触发 LLM 合并                 │
├──────────────┼──────────────────┼─────────────────────────────────────┤
│ REFINE       │ 仅新细节/改进    │ 同 CORROBORATE, 追加 Update 段落     │
│              │                  │ ≥3 次时触发 LLM 合并                 │
├──────────────┼──────────────────┼─────────────────────────────────────┤
│ CORRECT      │ 完整替换 body    │ 直接替换整个 body                    │
│              │ (旧内容有误)      │ (不用 Update 段落, 直接覆盖)          │
├──────────────┼──────────────────┼─────────────────────────────────────┤
│ SUPERSEDE    │ 完整重写 body    │ 重写 digest 卡片为当前状态             │
│              │ (用户显式变更    │ 旧事实不保留（历史在 daily 层）         │
│              │  状态/偏好)      │ frontmatter.status = "superseded"    │
│              │                  │ importance 取新值（不取 max）          │
└──────────────┴──────────────────┴─────────────────────────────────────┘
```

│      │  │
│      │  └── 结果: (same_nodes[:5], cross_nodes[:5])
│      │

│      │    - Existing Memory Files: same_nodes + cross_nodes 的内容

│      └── 调用 LLM
│
├── 5. 解析 LLM 返回
│      │
│      │  期望 JSON:
│      │  {

│      │    "wikilinks": ["derived_from:: [[...]]", ...]
│      │  }
│      │
│      └── 程序补全 wikilinks:
│           如果 LLM 忘了写 derived_from → 程序自动追加 (用之前算好的 provenance_links)
│           如果是 personal bucket 且忘了 relates_to → 程序自动追加
│
├── 6. 执行写入 (四层决策树)
│      │
│      │  ┌── 6a. SUPERSEDE + stable_key 命中 → _write_supersede
│      │  │    重写 digest 卡片为当前状态:
│      │  │      - body 完全替换为 final_content (旧事实不保留)
│      │  │      - 保留已有 derived_from 并追加新链接
│      │  │      - importance = 新值 (不取 max)
│      │  │      - frontmatter.status = "superseded"
│      │  │
│      │  ├── 6b. stable_key 命中 → 强制合并 (最高优先级)
│      │  │    即使 LLM 说 CREATE → 强制改为 REFINE
│      │  │    调用 _write_update(top_path=merge_path, action, ...)
│      │  │
│      │  │    _write_update 的行为取决于 action:
│      │  │      CORROBORATE / REFINE:
│      │  │        → 在现有 body 末尾追加 "\n\n---\n## Update (日期)\n\n{新内容}"
│      │  │        → 但如果已经有 ≥3 个 Update 段落 → 触发 LLM 合并 (_try_merge_updates)
│      │  │          LLM 用 _MERGE_UPDATE_PROMPT 将所有 Update 段落合并进正文
│      │  │          合并成功 → 替换整个 body（移除 Update 段落）
│      │  │          合并失败 → fallback 继续追加（允许暂时 >3）
│      │  │        → 如果新内容已经在 body 里 → 不追加 (防重复)
│      │  │
│      │  │      CORRECT:
│      │  │        → 直接替换整个 body (不是追加)
│      │  │
│      │  │      其他:
│      │  │        更新 frontmatter:
│      │  │          importance = max(旧, 新)
│      │  │          tags = 合并去重 (最多 10 个)
│      │  │          updated_at = 今天
│      │  │          如果 stable_key 为空 → 补上
│      │  │        如果 name 变了 → 追加 relates_to wikilink 指向新 name
│      │  │
│      │  │    成功 → 返回 action.lower()
│      │  │    archived → 返回 "skipped"
│      │  │
│      │  ├── 6c. LLM 说不是 CREATE + 有 same_nodes → 走 _write_update
│      │  │    取 same_nodes[0] 作为目标文件
│      │  │    (这是 LLM 自己判断"有类似的"但 stable_key 没命中的情况)
│      │  │
│      │  └── 6d. 以上都不匹配 → 走 _write_create
│      │       创建全新的 digest 文件:
│      │         digest/<bucket>/[agents/<id>/|shared/]<name>.md
│      │         frontmatter: source="auto_dream", stable_key 写入
│      │         body = final_content (含 wikilinks)
│      │         FileCatalog.upsert()
│      │       返回 "created"
│
└── 返回: "created" | "refined" | "corroborate" | "corrected" | "superseded" | "skipped"

#### stable_key — 合并键的作用

`stable_key` 是 auto_dream integrate 步骤中判断"新内容是否应该合并到已有 digest"的关键。它的作用是**跨标题变体去重**——即使 LLM 每次给记忆起的名字不同，只要 stable_key 相同就会合并到同一个文件：

```
情景: 第一次 auto_dream 提取了一个 unit 叫 "DB Selection"
      第二次 auto_dream 提取了一个 unit 叫 "Database Choosing Strategy"

      两个名字不同，但 make_stable_key() 都生成 "proc.db.selection"

      → integrate 步骤通过 stable_key 找到已有 digest 文件
      → 走 REFINE 路径（追加内容），而不是 CREATE 新文件
```

stable_key 的生成规则（见 `buckets.py:make_stable_key`）：
- `personal` bucket：识别身份/兴趣/规则等模式，生成 `user.identity.profile`、`user.interest.music.xxx` 等
- `procedure` bucket：`proc.<slugified_name>`
- `wiki` bucket：`wiki.<slugified_name>`
- LLM 可以显式指定 `stable_key`，优先于自动生成

#### 降级逻辑

| 组件缺失                  | 降级行为                                             |
| --------------------- | ------------------------------------------------ |
| `_generate_fn` 为 None | auto_dream 完全跳过（不调用 LLM），记录 warning              |
| FileCatalog 无变更记录     | extract 步骤 fallback：扫描最近 7 天的 daily/ 目录          |
| NodeSearch 不可用        | integrate 步骤跳过已有节点搜索，LLM 只看新 unit → 总是 CREATE    |
| LLM 返回非 JSON          | extract/integrate/topics 各步独立 try-catch，失败返回空/跳过 |
| extract 返回 0 个 units  | 整个 auto_dream 提前返回，不执行 integrate/topics          |

## 5. 检索引擎 (search/)

### 5.1 BM25Index — SQLite FTS5 全文索引

**文件**：`search/bm25_index.py`

使用 SQLite FTS5 虚拟表 + jieba 中文分词。

**表结构**：

```sql
CREATE VIRTUAL TABLE memory_fts USING fts5(
    path,       -- 文件路径（workspace 相对）
    name,       -- frontmatter.name
    content,    -- 索引文本 (name + description + body，去掉 predicate wikilink 行)
    agent_id,   -- 关联 Agent
    bucket,     -- daily | procedure | personal | wiki
    tags,       -- frontmatter.tags 空格连接
    tokenize = 'unicode61'
);
```

**分词策略**：
- 优先使用 `jieba.cut(text, cut_all=False)` 精确模式
- jieba 不可用时 fallback：ASCII 单词 + CJK unigram + bigram
- 输出空格分隔的 token 序列，FTS5 `unicode61` tokenizer 将每个 piece 作为一个 token

**搜索**：

```sql
SELECT path, bm25(memory_fts) as score
FROM memory_fts
WHERE memory_fts MATCH ?       -- tokenized query
  AND bucket = ?                -- optional
  AND (agent_id = ? OR agent_id = '')  -- optional: include global
ORDER BY score ASC LIMIT ?
```

注意：FTS5 的 `bm25()` 函数返回值越小表示越相关，代码中取负数 `-row[1]` 使其变为"越大越相关"。

### 5.2 VectorIndex — SQLite BLOB 向量存储

**文件**：`search/vector_index.py`

将 embedding 存为 packed float32 BLOB，搜索时全量加载 + 逐条计算 cosine similarity。

**表结构**：

```sql
CREATE TABLE memory_vectors (
    path TEXT NOT NULL,
    chunk_idx INTEGER NOT NULL,
    chunk_text TEXT NOT NULL,
    embedding BLOB NOT NULL,     -- struct.pack(f"{dim}f", *embedding)
    agent_id TEXT DEFAULT '',
    bucket TEXT DEFAULT '',
    PRIMARY KEY (path, chunk_idx)
);
```

**关键特性**：
- **维度一致性校验**：首次 add 记录维度 `_dim`，后续 add/search 校验维度匹配
- **暴力搜索**：全量加载所有 BLOB → `struct.unpack` 解包 → 逐条计算 cosine similarity → 排序取 top-k
- **文件级聚合**：`HybridSearch._vector_search()` 对同一 path 的多个 chunk 取最高分
- **适用规模**：<10k chunks（注释明确说明）

### 5.3 MarkdownChunker — 语义分块

**文件**：`search/chunker.py`

按 Markdown 标题层级（`##` 和 `###`）分块，每个 chunk 包含上下文信息。

**分块流程**：

```
MemoryFile
   │
   ├── 构建 prefix = name + description (全局前缀，注入每个 chunk)
   │
   ├── _split_by_headings(body)
   │    按 ^#{2,3}\s 正则分割
   │    维护标题栈: ## 入栈, ### 入栈
   │    section_path = "标题1 > 标题2" (breadcrumb)
   │
   ├── _merge_short(sections)
   │    相邻短段 (< min_chunk_size=100) 合并
   │
   └── _split_long(text)
        超长段 (> chunk_size=512) 在段落边界 (\n\n) 切分
        无段落边界时按行切分
        
最终 chunk.text = prefix + "\n" + section_path + "\n" + section_body
```

**具体示例**：

假设有一个记忆文件：

```markdown
# 项目会议记录

## 周一讨论
周一我们讨论了 API 设计。决定用 REST 风格。

## 周三评审
周三做了技术评审。
### 数据库选型
选了 PostgreSQL 而非 MySQL，因为需要 JSONB 支持。
### 缓存方案
用 Redis 做会话缓存，TTL 设为 30 分钟。
```

**Step 1 — 构建 prefix**：取文件名/标题作为全局前缀，注入每个 chunk。

```
prefix = "项目会议记录"
```

**Step 2 — 按标题切割（`_split_by_headings`）**：用正则 `^#{2,3}\s` 按 `##` / `###` 标题分割，维护标题栈生成面包屑路径。

| # | section_path（面包屑） | section_body |
|---|------------------------|--------------|
| 1 | `周一讨论` | `周一我们讨论了 API 设计。决定用 REST 风格。` |
| 2 | `周三评审 > 数据库选型` | `选了 PostgreSQL 而非 MySQL，因为需要 JSONB 支持。` |
| 3 | `周三评审 > 缓存方案` | `用 Redis 做会话缓存，TTL 设为 30 分钟。` |

**Step 3 — 合并短段（`_merge_short`）**：假设 `min_chunk_size=50`，第 1 段只有 20 个字符，太短，与第 2 段合并。

| # | section_path | section_body |
|---|--------------|--------------|
| 1 | `周一讨论 > 周三评审 > 数据库选型` | `周一我们讨论了 API 设计。决定用 REST 风格。\n选了 PostgreSQL 而非 MySQL，因为需要 JSONB 支持。` |
| 2 | `周三评审 > 缓存方案` | `用 Redis 做会话缓存，TTL 设为 30 分钟。` |

**Step 4 — 切分长段（`_split_long`）**：假设 `chunk_size=100`，某段超过 100 字符时，在 `\n\n`（段落边界）处切分；无段落边界时按行切分。本例中无超长段，跳过此步。

**Step 5 — 组装最终 chunk**：每个 chunk = `prefix + "\n" + section_path + "\n" + section_body`。

```
[chunk 1]
项目会议记录
周一讨论 > 周三评审 > 数据库选型
周一我们讨论了 API 设计。决定用 REST 风格。
选了 PostgreSQL 而非 MySQL，因为需要 JSONB 支持。

[chunk 2]
项目会议记录
周三评审 > 缓存方案
用 Redis 做会话缓存，TTL 设为 30 分钟。
```

**各步骤的设计意图**：

| 步骤 | 为什么这么做 |
|------|-------------|
| 按标题切 | 标题下的内容是一个语义整体，不应被拆散 |
| 带面包屑路径 | 搜索命中后，用户能看到"这段话属于哪个章节" |
| 带全局 prefix | 即使 chunk 被单独检索，也能知道它来自哪个文件 |
| 短段合并 | 避免产生"API 设计。"这种没头没尾的无意义片段 |
| 长段切分 | 防止一个 chunk 塞了太多内容，导致 embedding 不够精准 |

### 5.4 HybridSearch — BM25+Vector RRF 融合

**文件**：`search/hybrid_search.py`

两路检索 + Reciprocal Rank Fusion 融合 + Rerank 重排序 + Daily TTL 过滤 + wikilink 后处理。

#### 搜索流程

```
query
   │
   ├── Phase 1a: BM25 搜索
   │    bm25.search(query, top_k=k*2, agent_id, bucket)
   │    → bm25_ranked = {path: rank}  (1-based rank, 1=best)
   │
   ├── Phase 1b: Vector 搜索 (当 embed_fn + vector_index 可用时)
   │    query_emb = embed_fn(query)
   │    hits = vector_index.search(query_emb, top_k=k*2, agent_id, bucket)
   │    → 文件级聚合: 同 path 取最高分 chunk
   │    → vector_ranked = {path: rank}
   │
   ├── Phase 2: RRF 融合 (wikilink 不参与)
   │    for path in (bm25_ranked ∪ vector_ranked):
   │        bm25_component = bm25_weight * (1 / (rrf_k + bm25_rank))
   │        vector_component = vector_weight * (1 / (rrf_k + vector_rank))
   │        rrf_score = bm25_component + vector_component
   │    → 按 rrf_score 降序取 top-k*2
   │
   ├── Phase 3: Rerank 重排序
   │    for path in top-k*2:
   │    │   frontmatter = read frontmatter
   │    │   importance = frontmatter.get("importance", 0.5)
   │    │   decay = 0.5^(days_since_access / half_life)
   │    │         (基于 access_stats.last_accessed，无记录时 fallback 到 updated_at)
   │    │   recency = 0.5 + 0.5 / (1 + days_old / 30)
   │    │         (logistic 衰减，0天→1.0, 30天→0.73, 90天→0.55)
   │    │   importance_factor = 0.5 + importance  (映射 [0,1] → [0.5,1.5])
   │    │   rerank_score = rrf_score * importance_factor * decay * recency
   │    → 按 rerank_score 降序取 top-k
   │
   ├── Phase 4: Daily TTL 过滤
   │    for path in top-k:
   │    │   if path 在 daily/ 目录:
   │    │      created_at = frontmatter.created_at
   │    │      age_days = (今天 - created_at).days
   │    │      has_digest_inlink = wikilink 图中 inlinks 有 digest/ 开头的源
   │    │      if age_days > daily_ttl_days and has_digest_inlink:
   │    │         → 排除（已被蒸馏且过期的 daily 卡片）
   │    → 返回过滤后的结果
   │
   └── Phase 5: 加载内容 + archived 降权 + AccessStats 记录
        for path in filtered top-k:
        ├── read_markdown(path) → MemoryFile
        ├── archived 节点: BM25 分量 *= 0.5 (重新计算 rrf 分数)
        ├── access_stats.record(path)  ← fire-and-forget 记录访问
        └── 构建 SearchResult (无 expansion 字段，惰性构建)
```

#### SearchResult 数据结构

```python
@dataclass
class SearchResult:
    path: str                    # workspace 相对路径
    name: str                    # frontmatter.name
    content: str                 # body 正文
    score: float                 # RRF 综合分数（Rerank 后的最终分数）
    source: str                  # "bm25" | "vector" | "rrf"
    frontmatter: dict            # 完整 frontmatter
    scores: dict                 # {"bm25": float, "vector": float, "rrf": float}
```

**注意**：`expansion` 不再是 `SearchResult` 的字段。wikilink 邻居元数据通过 `HybridSearch.build_expansion(path)` 方法**惰性构建**——仅在调用方需要时才查询 wikilink 图，避免在搜索热路径上为每个结果都构建邻居数据。

#### Rerank 重排序

RRF 融合后，结果会经过 Rerank 重排序（`memory_rerank_enabled` 控制开关），综合考虑三个因素：

| 因子 | 来源 | 计算方式 | 范围 |
|------|------|---------|------|
| `importance_factor` | frontmatter.importance | `0.5 + importance`（映射 [0,1] → [0.5,1.5]） | 0.5-1.5 |
| `decay` | AccessStats last_accessed | `0.5^(days_since_access / half_life)`，无记录时 fallback 到 updated_at | 0.0-1.0 |
| `recency` | frontmatter.updated_at | `0.5 + 0.5 / (1 + days_old / 30)`（logistic 衰减） | 0.5-1.0 |

```
rerank_score = rrf_score × importance_factor × decay × recency
```

这使得高重要性、最近被访问过、最近创建/修改的记忆在排序中获得更高权重。recency 作为 tiebreaker 而非主导因素（30天仅降到 ~0.73）。

#### Daily TTL 过滤

搜索结果中的 daily 卡片会经过 TTL 过滤：

- 从 `frontmatter.created_at` 解析日期
- 如果 `age_days > daily_ttl_days`（默认 30 天）**且** 该卡片已被蒸馏（即 wikilink 图中有来自 `digest/` 的 inlink）
- 则从结果中排除——因为旧 daily 卡片的内容已被精炼到 digest，不需要再召回原始卡片
- 未蒸馏的 daily 卡片（无 digest inlink）不受 TTL 限制，确保未处理的卡片始终可被检索
- 文件和索引不被修改——这是纯查询期过滤

#### 降级逻辑

- `embed_fn` 为 None → 退化为纯 BM25
- `vector_index` 为 None → 退化为纯 BM25
- `vector_index.count() == 0` → 退化为纯 BM25
- query embedding 生成异常 → 退化为纯 BM25（记录 warning）

### 5.5 NodeSearch — digest-only 节点级搜索

**文件**：`search/node_search.py`

专门为 `auto_dream` 的 integrate 步骤设计的搜索，只查 `digest/` 目录的文件，按文件级聚合。

**与 HybridSearch 的区别**：

| 维度 | HybridSearch | NodeSearch |
|------|-------------|------------|
| 范围 | daily + digest | 仅 digest |
| 向量搜索 | 支持 | 不支持（仅 BM25） |
| wikilink 后处理 | 支持（build_expansion 惰性构建） | 支持（BFS 扩展，排除 derived_from 谓词） |
| agent_id 过滤 | 支持 | 不支持（跨 Agent 召回） |
| Rerank | 支持（importance_factor × decay × recency） | 不支持 |
| Daily TTL | 支持 | 不支持（不搜 daily） |
| 用途 | 通用记忆检索 | auto_dream integrate 时召回已有 digest 节点 |

**BFS 扩展特殊处理**：当直接 BM25 搜索无 digest 命中时，从 daily/ 的 BM25 命中作为种子，沿 wikilink 图扩展 1 跳，但排除 `derived_from` 谓词（避免 provenance 边引入噪音）。

### 5.6 WikilinkExpander — 邻接图

**文件**：`search/wikilink_expander.py`

SQLite 表存储 wikilink 边：

```sql
CREATE TABLE wikilinks (
    source_path TEXT NOT NULL,
    target_path TEXT NOT NULL,
    predicate TEXT,                    -- NULL 表示普通 wikilink
    PRIMARY KEY (source_path, target_path, predicate)
);
-- 索引: source_path, target_path, predicate
```

**关键方法**：

| 方法 | 说明 |
|------|------|
| `add_edges(source, targets, predicate)` | 批量添加边（统一 predicate） |
| `add_edges_detailed(source, links)` | 添加边（每条边独立 predicate） |
| `remove_edges_for(source)` | 删除某文件的所有出边 |
| `remove_all_for(path)` | 删除某文件的所有出入边 |
| `expand(seeds, max_hops, exclude_predicates)` | BFS 扩展（默认 1 跳），可排除指定谓词 |
| `get_outlinks(path, predicate)` | 获取出边（可选 predicate 过滤） |
| `get_inlinks(path, predicate)` | 获取入边（可选 predicate 过滤） |
| `remove_broken_links(existing_paths)` | 清理 target 不存在的边 |

### 5.7 AccessStats — 访问统计 sidecar

**文件**：`access_stats.py`

AccessStats 是一个基于 SQLite 的**访问统计 sidecar**，记录记忆文件的访问信息（最后访问时间、访问次数），用于搜索 Rerank 和 Curator 治理。

存储在 `metadata/access_stats.db`，与其他索引数据库并列。

**表结构**

```sql
CREATE TABLE access_stats (
    path TEXT PRIMARY KEY,       -- 文件相对路径
    last_accessed REAL NOT NULL DEFAULT 0,          -- 最后访问时间 (timestamp)
    access_count INTEGER NOT NULL DEFAULT 0  -- 累计访问次数
);

-- Curator 治理用：连续 N 天低于阈值的水印追踪
CREATE TABLE access_watermark (
    path TEXT PRIMARY KEY,
    first_below_since REAL     -- 首次低于阈值的时间戳
);
```

**重要约束**：AccessStats 绝不写入记忆卡片文件或 frontmatter。frontmatter 变更会污染 FileCatalog 的 mtime 变更检测，导致 "召回 → dream 重复处理" 的 LLM 负载反馈循环。

#### 核心作用

1. **Rerank 衰减因子**：`get` 方法返回最后访问时间，由 HybridSearch `_rerank` 计算衰减系数 `0.5^(days_since_access / half_life)`
2. **Curator 治理**：Curator 夜间扫描时使用 AccessStats 的 `get` + `get_watermark` + `set_watermark` 实现 "连续 N 天低于 effective score 阈值 → 归档" 的 grace 机制
3. **水印追踪**：`access_watermark` 表记录卡片首次低于 effective score 阈值的时间戳，只有连续低于阈值超过 grace_days 天才触发归档

#### 关键方法

| 方法 | 调用时机 | 作用 |
|------|---------|------|
| `initialize()` | `MemoryService.initialize()` | 创建 SQLite 连接和两张表 |
| `record(path)` | 搜索命中时 | fire-and-forget 增量记录访问（count+1，更新 last_accessed） |
| `get(path)` | Rerank / Curator | 返回 `{last_accessed, access_count}` 或 None |
| `get_all()` | 调试/批量查询 | 返回所有路径的 `{path: {last_accessed, access_count}}` |
| `get_watermark(path)` | Curator 治理 | 返回 `first_below_since` 时间戳或 None |
| `set_watermark(path, timestamp)` | Curator 治理 | 设置/清除水印（None = 删除记录） |
| `close()` | `MemoryService.close()` | 关闭连接 |

#### 衰减计算

AccessStats 本身只存储 `last_accessed` 和 `access_count`，不直接计算衰减系数。衰减由 `HybridSearch._rerank` 和 `Curator._step_digest_governance` 各自按需计算：

**HybridSearch Rerank 中的 decay**（基于 `memory_decay_half_life_days`，默认 30）：

```
days_since_access = (now - last_accessed) / 86400
decay = 0.5 ^ (days_since_access / half_life)
# 半衰期 30 天 → 30 天未访问 decay = 0.5
# 无访问记录时 fallback 到 frontmatter.updated_at
```

**Curator 中的 effective score**（用于归档判定）：

```
decay = 0.5 ^ (days_since_access / half_life)
access_factor = log2(2 + access_count)
effective = importance × decay × access_factor
# 当 effective < archive_score 且持续 grace_days 天 → 归档
```

## 6. Preference 偏好系统

**文件**：`preference.py` + `memory_writer_compat.py`

PG KV 表 `user_preferences(user_id, key, value, source, updated_at)` 存储原子级用户偏好。

### 6.1 与 file-native personal bucket 的分工

| 维度 | Preference (PG KV) | digest/personal/ (Markdown) |
|------|-------------------|---------------------------|
| 存储形式 | key=value 键值对 | Markdown 规则卡片 |
| 内容量 | 原子级（值 ≤200 字符） | 短规则卡（≤900 字符） |
| 语义结构 | 无结构 | Rule + Why + How to apply |
| 提取方式 | 每轮用户消息后 LLM/规则提取 | auto_dream 从 daily 卡片精炼 |
| 使用场景 | "姓名=张三" "喜好=Python" | "用户偏好 TypeScript，因为..." |
| 注入方式 | ProfileSource → PromptAssembler | RecallSource → HybridSearch |

### 6.2 提取流程

```
on_message_end(role='user')
   │
   ├── LLM 可用 → extract_preferences_compat(generate_fn, msg, existing_keys)
   │    prompt (_PREFERENCE_EXTRACTION_PROMPT):
   │      - 只从 USER 消息提取
   │      - 提取: 姓名/职业/偏好/计划/健康/技能等
   │      - 稳定 key 命名（同义合并）
   │      - 输出: JSON 对象
   │    → Preference.set(key, value, source='extracted')
   │
   └── LLM 不可用 → _extract_rule_based(msg)
        规则: "我喜欢X" → 喜好=X
              "我叫X"   → 姓名=X
              "我住在X" → 所在地=X
              ...
```

### 6.3 同义词归一

`_KEY_SYNONYMS` 字典将常见中文同义词映射到统一 key：

```python
{
    "喜欢": "喜好", "偏好": "喜好", "偏爱": "喜好", "爱好": "喜好",
    "名字": "姓名", "名称": "姓名",
    "编程语言": "语言", "编程偏好": "语言",
}
```

### 6.4 值长度限制

- `source='extracted'` 的值截断到 200 字符（`_PREFERENCE_VALUE_MAX`）
- `source='manual'` 的值不受限制（用户手动设置）
- `extracted` 不能覆盖 `manual`（手动设置的优先级更高）

### 6.5 缓存

偏好读取通过 `app.infra.cache.get_cache()` 获取统一的缓存抽象层实例，key = `user_prefs:{user_id}`，TTL 120 秒。写入（`set` / `save_batch`）或删除后自动调用 `_invalidate_cache()` 失效缓存。

缓存的具体实现由 `app.infra.cache` 模块决定（在双 DB 架构下为进程内 dict TTL 缓存），`Preference` 类本身不关心缓存底层机制，只通过 `cache.get_or_load(key, ttl, loader_fn)` 和 `cache.delete(key)` 两个接口交互。

## 7. MemoryService 编排门面

**文件**：`memory_service.py`

### 7.1 初始化

```python
async def initialize(self):
    # 1. 初始化工作区目录
    self.workspace.initialize()
    
    # 2. 初始化五个 SQLite 索引
    self.bm25.initialize()
    self.wikilink_expander.initialize()
    self.file_catalog.initialize()
    self.vector_index.initialize()
    self.access_stats.initialize()
    
    # 3. 文件目录与磁盘对账
    self.file_catalog.reconcile(daily_dir, digest_dir)
    
    # 4. 构建 HybridSearch
    self._search = self._build_search()
    
    # 5. 全量重建索引
    self.auto_index.full_reindex()
```

### 7.2 运行时注入

```python
def set_embed_fn(self, fn):       # 注入 embedding 函数

DIGEST_BUCKETS = ("procedure", "personal", "wiki")

### 8.2 Bucket 语义

| Bucket | 语义 | Body 形状 | 主体形式 |
|--------|------|----------|---------|
| `procedure` | 可复用 how-to / runbook / 调试策略 | Trigger / Steps / Pre-conditions / Failure Modes | "When X, do steps…" |

| `wiki` | 可复用知识/概念/技术事实 | Definition / Properties / Context | "X is… / X includes…" |

### 8.3 stable_key — 合并键

`make_stable_key(bucket, name, explicit)` 生成跨标题变体的合并键：

- `personal` bucket: 识别身份/兴趣/规则等模式，生成 `user.identity.profile`、`user.interest.music.doudou` 等
- `procedure` bucket: `proc.<slugified_name>`
- `wiki` bucket: `wiki.<slugified_name>`
- 显式 `explicit` 参数优先

### 8.4 validate_and_normalize_unit — 程序门控

LLM extract 之后的程序验证，不依赖 prompt：

| 检查 | 行为 |
|------|------|
| delivery/项目状态内容误标 personal | 有 runbook 信号 → rebucket procedure；否则 drop |
| runbook 形式误标 personal | rebucket procedure |
| 百科内容误标 personal | 截断为短规则卡；截断后无用户主体信号 → rebucket wiki |
| personal 超长 | 截断到 900 字符 |

### 8.5 个人内容截断

`_shorten_personal_content(content, summary)` 保持 personal bucket 的短规则卡形态：

1. 提取 Rule 句子（优先 summary，否则取第一个非标题非 provenance 行）

## 9. Agent 工具集成

**文件**：`tools/memory_store.py` + `tools/manage_memory.py`

### 9.1 工具清单

| 工具名 | 类型 | 说明 |
|--------|------|------|
| `memory_recall` | 自动注入（SDK agent，非 guide） | 混合检索记忆 + 返回偏好上下文 + related 链接元数据 |
| `memory_read` | 自动注入（SDK agent，非 guide） | 按路径读取单张记忆卡，沿 wikilink 多跳遍历 |
| `memory_store` | 条件注入（SDK agent + `memory_enabled=true`） | Agent 主动写入 digest 记忆 |
| `memory_proactive` | 注册但未自动注入 | 获取主动话题（工具已注册，当前无注入路径） |
| `manage_memory` | Guide Agent 专属 | 记忆管理（list/delete/consolidate） |

### 9.2 memory_recall — 记忆召回

```
Agent 调用 memory_recall({ query: "...", top_k: 5 })
   │
   ├── MemoryService.recall(query, top_k, agent_id, user_id)
   │    → HybridSearch.search() → list[SearchResult]
   │    → 返回 memories 数组（含 name/content/score/source/path）
   │
   ├── 为每条结果构建 related 链接元数据
   │    → svc.build_expansion(r.path) → {outlinks[], inlinks[]}
   │    → _slim_related(): 每边截断至 5 条，仅保留 {path, name, predicate}
   │      (不含 description — 工具路径按 token 精简)
   │
   ├── MemoryService.get_preference_context(user_id)
   │    → 内部调用 Preference(user_id).load_from_storage() 从 PG 加载
   │    → Preference.build_context() → "【用户偏好】\nkey: value\n..."
   │    → 注意：偏好数据按 user_id 隔离，与记忆检索的 agent_id 无关
   │
   └── 返回: { memories: [...], preferences: "..." }
```

**related 字段**：每条记忆附带 `related` 邻接元数据，包含 `outlinks`（该记忆指向的文件）与 `inlinks`（指向该记忆的文件）两个列表。每个条目含 `path`、`name`、`predicate`（如 `derived_from`、`relates_to` 或空），每边上限 5 条。`related` 中的条目仅包含实际存在的记忆文件（断链自动剔除）。agent 可沿 `related` 中的路径调用 `memory_read` 进行多跳遍历——例如 digest 卡的 `derived_from` outlink 指向 daily 卡（含完整历史），daily 卡的 inlinks 指向蒸馏它的 digest 卡（最新结论）。

**工具描述**：`memory_recall` 描述为 "Search long-term memory with keyword (BM25) + vector semantic recall"，并说明 `related` 字段与 `memory_read` 的配合用法。不再宣称 "hybrid BM25 + wikilink search"（wikilink 不参与排序，仅作遍历通道）。

**preferences 字段来源说明**：`preferences` 是一个字符串（不是对象/数组），内容是 `Preference.build_context()` 的输出。当用户没有任何偏好时返回空字符串 `""`。偏好数据独立于文件记忆系统，存储在 PG `user_preferences` 表中，按 `user_id` 隔离。`memory_recall` 工具同时返回记忆检索结果和用户偏好，让 Agent 在一次工具调用中获取完整的用户上下文。

**自动注入**：SDK (Custom) agent 在 `build_adapter_input` 时自动注入 `memory_recall`（prepended to tool list）。CLI agent 和 Guide agent 不注入。`memory_read` 与 `memory_recall` 同条件注入（SDK agent + memory 开启时隐式注入列表同时加入两者）。

### 9.3 memory_store — Agent 主动存储

```
Agent 调用 memory_store({ name: "...", content: "...", bucket: "procedure", importance: 0.8 })
   │
   ├── 条件注入: SDK agent + memory_enabled=true 时自动注入（非 UI 勾选）
   ├── 限流: 每 agent run 最多 3 次写入 (MAX_WRITES_PER_RUN)
   ├── 内容限制: 最多 500 字符 (MAX_CONTENT_LENGTH)
   ├── bucket 限制: 只能 "procedure" 或 "wiki" (不允许 personal)
   │
   ├── 构造 MemoryFrontmatter(source=f"agent:{agent_id}")
   ├── workspace.digest_path(bucket, name, agent_id)
   ├── write_markdown(filepath, fm, content)
   └── auto_index.index_file(filepath) → 增量索引
```

### 9.4 manage_memory — Guide Agent 管理工具

```
manage_memory({ action: "list" | "delete" | "consolidate", memory_type: "long_term" | "preference" })
   │
   ├── list long_term → 列出记忆文件 (digest + daily)
   ├── list preference → 列出偏好键值对
   ├── delete → 删除记忆文件/偏好 (需 confirm=true)
   └── consolidate → 触发 auto_dream 精炼
```

### 9.5 memory_read — 按路径读取记忆卡

```
Agent 调用 memory_read({ path: "digest/wiki/react-19.md" })
   │
   ├── 路径校验
   │    ├── normalize: path.replace("\\", "/").lstrip("/")
   │    ├── 后缀检查: 必须以 .md 结尾
   │    ├── resolve 后必须位于 memory workspace root 内 (relative_to 检查)
   │    │   (拒绝 .. 逃逸，防止目录穿越)
   │    └── 违规返回明确错误，不泄露文件系统结构
   │
   ├── 读取文件
   │    ├── read_markdown(root / normalized) → MemoryFile
   │    ├── 文件不存在 → 返回 "Memory card not found" 类错误
   │    └── 提取 frontmatter: name / status / agent_id / bucket / importance
   │
   ├── 内容截断
   │    └── len(body) > MAX_READ_CONTENT_LENGTH (2000) → 截断前缀 + truncated=True
   │
   ├── 构建 related (复用 build_expansion + _slim_related)
   │    → outlinks/inlinks 各限 5 条，含 {path, name, predicate}
   │
   └── 返回: { path, name, content, status, agent_id, bucket, importance, related, truncated }
```

**链接可达即授权**：`memory_read` 不施加 agent 软隔离（与 search 的 `agent_id = ? OR agent_id = ''` 规则不同）。dream 的 weave 与 NodeSearch 本就是跨 agent 设计，图上会存在 A 的卡链接 B 的卡；若按 search 规则隔离，链接会死在半路。图本身即权限边界（只能到达被链接暴露的文件）。返回值带 `agent_id` 作溯源标注。

**多跳遍历**：agent 读取某张卡后，可继续访问其 `related` 中列出的另一张卡——再次按路径调用 `memory_read` 即可获得新卡，遍历深度不受工具限制。双重上限兜底防止 token 暴走：`related` 每边 5 条 + 单卡正文 2000 字符截断。

**status 字段**：返回值包含 `status`（`active` / `archived` / `superseded`），agent 可自行判断信息时效。`superseded` 表示用户显式变更状态后重写的卡片，旧事实不保留。

**自动注入**：与 `memory_recall` 同条件注入——SDK (Custom) agent 在 `build_adapter_input` 时隐式注入列表同时加入 `memory_recall` 和 `memory_read`。CLI agent 和 Guide agent 不注入。

## 10. PromptAssembler 注入

**文件**：`services/prompt_assembler.py`

记忆系统通过两个 ContextSource 注入 Agent 的 system prompt：

### RecallSource — 记忆语义检索注入

```python
class RecallSource(ContextSource):
    async def fetch(self, slot, q):
        results = await self._memory.recall(q.text, top_k=slot.filter.top_k or 3, agent_id=q.agent_id)
        return [ContextItem(text=item.content, score=item.score, source="recall",
                            meta={"importance": ..., "name": ...}) for item in results]
```

填充 `SlotRecall` 槽位，将记忆检索结果注入 system prompt。

### ProfileSource — 偏好注入

```python
class ProfileSource(ContextSource):
    async def fetch(self, slot, q):
        prefs = await get_user_preferences_cached(q.user_id)
        # 按 classify_memory_content + _IMPORTANCE_BY_CATEGORY 计算分数
        # 按 score 降序排列
        # 按 token budget 截断
        return [ContextItem(text=f"{k}: {v}", score=..., source="profile") for k, v in prefs]
```

填充 `SlotProfile` 槽位，将用户偏好注入 system prompt。

### 槽位优先级

PromptAssembler 内置的 RuntimeContextSchema 定义了槽位优先级和 token budget 分配。recall 和 profile 槽位通常在中低优先级，确保核心指令和工具说明优先填充。

## 13. 数据流总览

### 13.1 写入流（对话 → 记忆）

```
用户消息
   │
   ├─ on_message_end(role='user')
   │    └─ 偏好提取 → PG user_preferences 表
   │
   └─ Agent 回复
        └─ on_message_end(role='assistant')
             ├─ 从 PG ChatHistory 读取最后一条 user 消息
             ├─ auto_memory (后台)
             │    ├─ LLM 提取事实 → daily/<date>/<name>.md
             │    │    └─ file_catalog.upsert(path, st_mtime=0, bucket="daily")
             │    │       (写入 pending 标记)
             │    ├─ session JSONL 双写 → session/<conv>.jsonl
             │    └─ auto_index 增量索引
             │         ├─ BM25 (FTS5)
             │         ├─ Wikilink 图
             │         ├─ FileCatalog
             │         └─ VectorIndex (chunk + embed)
             │
             └─ auto_dream 阈值检查
                  ├─ count_changed("daily") ≥ threshold (5)
                  └─ cooldown 检查通过 → auto_dream (后台)
                       ├─ extract: FileCatalog.get_changed → LLM 从 daily 提取抽象
                       ├─ integrate: LLM + node_search → digest 写入
                       │    └─ SUPERSEDE / CREATE / CORROBORATE / REFINE / CORRECT
                       └─ topics: LLM 选择 → interests.yaml

Curator 夜间定时 (auto_dream_cron=23:00)
   ├─ Step 1: auto_dream (增量精炼)
   ├─ Step 2: daily governance (过期卡片日志)
   ├─ Step 3: digest governance (低分卡片归档 → AccessStats)
   └─ Step 4: full reindex (全量重建索引)
```

### 13.2 读取流（检索 → 注入）

```
Agent 运行时
   │
   ├─ 方式 1: Agent 主动调用 memory_recall 工具
   │    └─ HybridSearch.search(query)
   │         ├─ BM25 搜索
   │         ├─ Vector 搜索 (可选)
   │         ├─ RRF 融合
   │         ├─ Rerank 重排序 (importance_factor × decay × recency)
   │         ├─ Daily TTL 过滤 (排除已蒸馏且过期的 daily 卡片)
   │         ├─ AccessStats 记录访问
   │         └─ build_expansion 惰性构建 related (outlinks/inlinks)
   │            → _slim_related: 每边 5 条，含 {path, name, predicate}
   │
   ├─ 方式 1b: Agent 沿 related 链接调用 memory_read 工具
   │    └─ memory_read({ path: "digest/wiki/react-19.md" })
   │         ├─ 路径校验 (resolve + .md 后缀 + workspace root 内)
   │         ├─ read_markdown → 返回 name/content/status/agent_id/bucket
   │         ├─ 内容截断 (≤2000 字符)
   │         └─ build_expansion → related (可继续多跳遍历)
   │
   ├─ 方式 2: PromptAssembler 自动注入
   │    ├─ RecallSource → recall slot → 记忆检索结果 (不含 related，零邻接开销)
   │    ├─ ProfileSource → profile slot → 用户偏好
   │    └─ Proactive → proactive context → 主动话题
   │
   └─ 方式 3: API 查询
        ├─ GET /api/memory/search → 混合检索 (含完整 expansion 含 description)
        ├─ GET /api/memory/files → 文件列表
        └─ GET /api/memory/proactive → 主动话题
```

## 15. Curator 夜间治理

**文件**：`curator.py`

Curator 是记忆系统的**夜间治理器**。它在设定的 cron 时间（默认 23:00）自动执行四步管线，完成记忆的增量精炼、过期清理、低价值归档和索引重建。

### 15.1 触发机制

- **定时触发**：`CuratorJob` 按 `memory_auto_dream_cron`（默认 `"23:00"`）定时执行
- **手动触发**：`POST /api/memory/auto-dream`（仅执行 auto_dream 步骤，非完整四步管线）

### 15.2 四步管线

```
CuratorJob.run()
│
├── Step 1: auto_dream (增量精炼)
│    调用 auto_dream.run(max_units)
│    ├─ extract: FileCatalog.get_changed → LLM 从 pending daily 卡片提取抽象
│    ├─ integrate: LLM + NodeSearch → digest 写入 (CREATE/CORROBORATE/REFINE/CORRECT/SUPERSEDE)
│    └─ topics: LLM 选择 → interests.yaml
│    (与 §4.3 描述的三步管线完全一致)
│
├── Step 2: daily governance (daily 卡片治理)
│    ├─ 扫描 daily/ 目录下所有卡片
│    ├─ 对超过 daily_ttl_days 且无 digest inlink 的卡片记录日志
│    │   (过期且未蒸馏的卡片 → 优先触发 dream 精炼)
│    └─ 不删除，仅记录待处理列表
│
├── Step 3: digest governance (digest 卡片治理)
│    ├─ 遍历 digest/ 下所有非 archived 卡片
│    ├─ 计算 effective = importance × decay × log2(2 + access_count)
│    │   decay = 0.5^(days_since_access / half_life)
│    │   days_since_access 取自 AccessStats.last_accessed
│    │   access_count 取自 AccessStats.access_count
│    ├─ effective < archive_score → 检查 access_watermark
│    │   ├─ 无水印 → 设置 first_below_since = now (首日低于阈值)
│    │   ├─ 有水印且 days_below >= archive_grace_days → 归档
│    │   │   → 更新 frontmatter.status = "archived"
│    │   │   → 清除水印
│    │   │   (归档后 BM25 搜索降权 0.5x)
│    │   └─ 有水印但未达 grace_days → 不操作
│    ├─ effective >= archive_score → 清除已有水印 (恢复)
│    └─ 记录归档日志
│
└── Step 4: full reindex (全量重建索引)
     调用 auto_index.full_reindex()
     ├─ 清空 BM25 / Wikilink / Vector 索引
     ├─ 遍历 daily/ + digest/ 所有 .md 文件重建
     └─ 清理断链 (remove_broken_links)
     (确保索引与磁盘文件完全一致)
```

### 15.3 与自动触发的区别

| 维度 | 自动触发 (阈值) | Curator 定时 |
|------|----------------|-------------|
| 触发条件 | pending 卡片 ≥ threshold + cooldown | cron 时间到 |
| 执行内容 | 仅 auto_dream 三步 | 完整四步管线 |
| 增量/全量 | 增量 (只处理 pending) | 增量 auto_dream + 全量 reindex |
| 治理操作 | 无 | daily 治理 + digest 归档 |
| 频率 | 对话驱动（可能一天多次） | 每天一次 |

### 15.4 降级逻辑

| 条件 | 降级行为 |
|------|---------|
| `memory_enabled = False` | Curator 完全跳过 |
| `memory_curator_enabled = False` | Curator 完全跳过 |
| LLM 不可用 | Step 1 auto_dream 跳过，Step 2-4 正常执行 |
| AccessStats 不可用 | Step 3 跳过归档，其他步骤正常 |
| auto_index 初始化失败 | Step 4 跳过，记录 warning |
