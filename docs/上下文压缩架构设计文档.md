## 1. 设计目标

### 1.1 核心问题

AChat 是一个多 Agent 协作平台，Agent 在长会话中面临三个上下文挑战：

1. **运行时上下文溢出** — 单次 ReAct loop 持续累积 tool_use/tool_result 消息，context window 逐渐填满
2. **跨 Run 上下文断裂** — 新 Run 启动时，旧 Run 的完整历史无法全量注入，需要压缩后注入
3. **会话级记忆缺失** — 用户离开后回来，Agent 不知道之前做了什么、决策了什么

### 1.2 设计原则

| 原则 | 含义 |
|---|---|
| **零 LLM 优先** | 运行时裁剪纯结构化，零 LLM 调用；LLM 仅用于 Session Note 提取 |
| **Action 优先** | agent 的 tool_call（决策行为）比 tool_result（观测数据）更重要，裁剪时优先保留 Action |
| **可恢复** | 被裁剪的 Observation 附带 recover hint，Agent 可主动重新获取 |
| **不阻断** | 压缩失败时降级而非报错，Agent 仍能正常对话 |
| **结构化优先** | Session Note 从非结构化文本升级为结构化 YAML 模板 |
| **单一 LLM 压缩点** | Session Note 是唯一的 LLM 压缩产物，不再有独立的全量 LLM 压缩层 |

### 1.3 关键设计决策

以下决策已在探索阶段确认：

| 决策点 | 选择 | 理由 |
|---|---|---|
| 手动压缩 (/compact) | **去除** | Session Note 已覆盖 LLM 提取需求，手动压缩冗余 |
| Session Note 结构化 | **保留并重构** | 从纯文本升级为 10-section YAML 模板 |
| Session Note 合并策略 | **方案 C: LLM 全量输出 + 分 section 差异化** | 保证语义正确和信息准确性 |
| 裁剪阈值 | 0.75 / 0.88 / 0.93 / 0.95 (固定) | 模型上下文窗口固定 200k，通用 mask 压缩率高，首次可更晚触发 |
| per-tool summarizer | **替换为通用 mask + 白名单** | 论文证实简单 masking 与 LLM 摘要效果相当；29 个 summarizer 映射维护成本过高 |
| LLM 全量压缩层 | **去除** | Session Note 已是 LLM 压缩产物；全量压缩重复处理 Discourse，收益有限 |

## 2. 现状架构

当前系统有四层压缩，分布在不同代码路径中：

```
┌─────────────────────────────────────────────────────────────────┐
│                     Agent ReAct Loop                            │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │  Tier 0: 运行时内存裁剪 (compact_pipeline.py)           │    │
│  │  五阶段: summarize → prune → fold → soft_inject →      │    │
│  │           force_final                                    │    │
│  │  纯 regex/结构化，零 LLM 调用                            │    │
│  │  阈值: 0.70 / 0.80 / 0.88 / 0.93 / 0.95                │    │
│  └──────────────────────────────────────────────────────────┘    │
│                              ↓ (Run 结束)                       │
└─────────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────┐
│  Tier 1: 异步增量摘要 (session_memory.py)                       │
│  后台 asyncio task，在 assistant 消息完成后触发                  │
│  阈值: tokens ≥ 10k + (增量 ≥ 5k 或 tool_calls ≥ 3)            │
│  产出: 非结构化 summary 文本 + covers_up_to 时间戳              │
│  存储: context_summaries 表, summary_type='session'              │
└─────────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────┐
│  Tier 2/3: 全量 LLM 压缩 (context_compaction_service.py)        │
│  触发: 手动 /compact 或自动 compaction hook                      │
│  三分支策略:                                                    │
│    Case 1: Session Memory 全覆盖 → 零 LLM 调用                  │
│    Case 2: Session Memory 部分覆盖 → gap + summary → LLM        │
│    Case 3: 无 Session Memory → full transcript → LLM           │
│  产出: ContextSummary (summary_type='compaction') + 系统消息     │
│  附带: 能力上下文恢复 (工具列表/附件/派发计划)                    │
└─────────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────┐
│  Tier 4: 跨 Run 序列化裁剪 (conversation_context.py)             │
│  新 Run 启动时执行 build_history_for()                           │
│  策略:                                                          │
│    1. 加载 latest ContextSummary 之后的所有消息                  │
│    2. 无 ContextSummary 时 fallback 到 SessionMemory             │
│    3. ratio ≥ 0.65 → prune_old_tool_results + fold_old_messages │
│    4. tool_result 重放上限 4000 字符                              │
│  产出: OpenAI 格式 chat messages list                           │
└─────────────────────────────────────────────────────────────────┘
```

|---|---|---|
| 重复工具调用 | 连续 3 次相同 fingerprint | soft_inject → force_final |

| 操作轮次上限 | max_tool_turns (用户配置) | soft_inject → force_final |

## 3. 问题分析

### 3.1 LLM 全量压缩层（Tier 2/3）收益有限

当前 Tier 2/3 的 `compact_conversation` 用 LLM 对历史消息做全量摘要。但分析发现：

**对话历史中有两类截然不同的内容**：

```
Type A: Observation (工具返回)
  • fs_read 的完整文件内容 (可能 5000+ token)
  • bash 的命令输出 (可能 2000+ token)
  • fs_list 的目录列表
  特征: 信息密度低、可重新获取、占比最大 (>70%)
  最适合: 结构化裁剪/masking (不需要 LLM)
  LLM 压缩收益: 低 — regex 裁剪已能砍掉 80%+

Type B: Discourse (对话本身)
  • user 的请求和追问
  • agent 的推理文本和决策
  • 多 agent 间的讨论
  特征: 信息密度高、不可重新获取、占比小 (<30%)
  最适合: LLM 摘要 (需要语义理解)
  结构化裁剪收益: 低 — 砍掉就丢信息
```

LLM 全量压缩处理的大头是 Observation（70%+），但这用结构化裁剪就能砍掉 80%+。真正需要 LLM 语义理解的 Discourse 占比小，而 Session Note 的增量 LLM 提取已经把 Discourse 的关键信息抽出来了。

**论文佐证**：
- "The Complexity Trap" (arXiv:2508.21433)：简单 observation masking 与 LLM summarization 在下游任务表现上效果相当
- NirDiamant 实验：摘要压缩在 5 轮一次时任务完成率最高（92%），1 轮一摘要反而掉到 71%

### 3.2 Tier 0 与 Tier 4 裁剪逻辑重复

`compact_pipeline.py` (Tier 0) 和 `conversation_context.py` (Tier 4) 各自独立实现了：

| 功能 | Tier 0 (compact_pipeline.py) | Tier 4 (conversation_context.py) |
|---|---|---|
| 轮次边界识别 | `find_turn_boundaries()` — dict 格式 | `_find_turn_boundaries_messages()` — ORM 格式 |
| 保留最近 N 轮 | `keep_recent_turns()` | `_keep_recent_turns_messages()` |
| Stage 1 摘要 | `_stage1_summarize()` — 修改 dict content | `prune_old_tool_results()` — 替换 parts_list |
| Stage 3 折叠 | `_stage3_fold()` — dict fold marker | `fold_old_messages()` — SimpleNamespace marker |
| 工具计数 | `_collect_tool_names_in_span()` | `_collect_tool_names_in_span_messages()` |

两套实现处理同一套逻辑，操作不同数据结构（dict vs ORM Message），维护成本翻倍且行为不一致。

### 3.3 29 个 per-tool summarizer 映射过度复杂

`compact_pipeline.py` 为 21 种工具注册了专用 summarizer（实际 29 个 key 映射，部分工具共用同一 summarizer），每个有 Stage 1/2 两个策略，共 42+ 个函数。但：

1. 通用 mask（保留 tool_name + key args + recover hint）的压缩率（98%）比 per-tool summarizer（84%）更高
2. agent 需要旧内容时可重新调一次工具恢复，成本极低
3. 29 个 summarizer 映射的维护成本远大于 "agent 重新读一次 outline" 的成本
4. 论文证实简单 masking 够用

### 3.4 Session Memory 结构简陋

当前 Session Memory 的摘要是一段非结构化自然语言：

```python
# session_memory.py 的 system prompt
"你是会话摘要助手。请将新增内容整合进已有摘要，保持摘要简洁但信息完整。"
"务必保留：用户核心目标、关键决策、已产出产物、待跟进事项。"
```

问题：
1. **消费方难以利用** — 只能当作一段文本注入 LLM prompt，无法按 section 提取
2. **无状态感知** — 无法区分「已完成的决策」和「待跟进的问题」
3. **增量合并语义不安全** — 纯文本追加无法处理矛盾覆盖和状态过期

### 3.5 阈值阶梯间距不合理

当前五阶段 0.70 / 0.80 / 0.88 / 0.93 / 0.95：

- Stage 1→2 间距 10%（200k = 20k，4-6 轮余量）— 尚可
- Stage 2→3 间距 8%（200k = 16k，3-5 轮）— 偏紧
- Stage 3→Soft 间距 5%（200k = 10k，2-3 轮）— 非常紧，一轮大输出就跳过
- Soft→Force 间距 2%（200k = 4k，1 轮）— 基本无缓冲

通用 mask 替代 summarizer 后，Stage 1 一次裁剪的压缩率从 84% 提升到 98%，不需要 Stage 2 再裁一次 observation（已经 mask 了）。五阶段可简化为三阶段。

### 3.6 ORM 对象意外修改风险

`conversation_context.py` 的 `_build_history_legacy` 路径在 `prune_old_tool_results` 之前调用了 `db.expunge_all()`，但 `_build_history_with_assembler` 路径缺少 `expunge_all()`。如果 assembler 路径触发了 prune/fold，ORM 对象的 `parts_list` 修改会被 auto-commit 写回 DB，导致持久化数据被意外裁剪。

### 3.7 Stage 反复横跳问题

ratio 在 Stage 1 门槛附近反复横跳会导致 `compact_consecutive_failures` 累积，最终 `compact_disabled = True`，跳过 Stage 2/3 直接进入 soft_inject / force_final。

## 4. 业界调研

### 4.1 Claude Code 的三层渐进式压缩

Claude Code 的上下文管理是三层渐进式压缩 + 多重自愈恢复：

```
Token 曲线:
0% ─────── 87% ────── 90% ────── 93% ────── 95% ────── 100%
正常运行     AutoCompact   警告提示    错误状态    阻塞      硬上限

第 1 层: Micro-Compact (每次 API 调用前)
  不改变对话结构，只清除过期工具返回内容
  触发: 距上次 assistant 消息 > 60 分钟，或单个工具结果超阈值
  操作: 将旧 tool_result 替换为 [stale tool result] 标记

第 2 层: Auto-Compact (token 阈值触发)
  完整 LLM 摘要生成 (用 Haiku，便宜快速)
  触发: effective_window - 13,000 tokens (~87%)
  流程: 分组 → 剥离图片 → LLM 摘要 → 恢复文件+技能
  Token 预算: 50K 给摘要上下文，5K/文件恢复 (最多 5 个)，25K 技能总额

第 3 层: Session Memory (后台异步)
  自动维护 Markdown 会话笔记，后台 fork 子 agent 提取
  10 section 结构化模板 (Current State / Key Files / Commands / Decisions / ...)
  与 Auto-Compact 配合: 压缩前优先尝试 Session Memory
  安全: 子 agent 只能编辑笔记文件路径

恢复机制 (Post-Compact Restoration):
  压缩后自动恢复最近操作的文件 (最多 5 个，每个 5K token)
  已加载的技能 (每个 5K，总额 25K)
  附件信息 + 进行中的 plan
```

**关键设计**：
- 用 **Haiku** 做压缩摘要（便宜、快），独立于主对话模型
- 压缩后**主动恢复**文件和技能上下文（直接把内容塞回来）
- Session Memory 是 **Markdown 文件**，结构化 10 section 模板
- 熔断器：连续 3 次失败停止尝试自动压缩

### 4.2 Pi Agent 的极简策略

Pi Agent 采用极简上下文管理：
- 只有 4 个工具：`read` / `write` / `edit` / `bash`
- 没有 MCP、没有子 agent、没有权限弹窗
- **每轮发送的上下文大约只有其他工具的 1/3**
- 长对话自动压缩
- 项目说明写入 `AGENTS.md` 按需加载技能文件

核心理念："不做什么"的设计哲学 — 上下文最少即最多。

### 4.3 论文参考

| 论文 | 核心发现 | 对我们的启示 |
|---|---|---|
| **The Complexity Trap** (arXiv:2508.21433) | 简单 observation masking 与 LLM summarization 效果相当 | 通用 mask 替代 per-tool summarizer 是可行的 |
| **ACON** (arXiv:2510.00615) | Action（决策）比 Observation（工具结果）更重要；应自适应决定压缩哪些 | Action 优先保留，Observation 积极 mask |
| **NirDiamant 实验** (LoCoMo benchmark) | 5 轮一次摘要完成率 92%，1 轮一摘要反而掉到 71% | 不要过于频繁地做 LLM 提取 |
| **Context Compression Survey** (自动化所+上交) | Agent 瓶颈从"模型能不能想"转向"上下文能不能被可靠管理" | 压缩系统是核心基础设施 |

### 4.4 对比分析

| 维度 | AChat 现状 | Claude Code | Pi Agent | 新方案 |
|---|---|---|---|---|
| 运行时裁剪 | 五阶段 per-tool summarizer | 三层渐进式 | 简单 masking | 三阶段通用 mask |
| 会话级摘要 | 非结构化文本 | 10-section Markdown | 无 | 10-section YAML |
| 跨 Run 恢复 | ContextSummary + SessionMemory | Session Memory 结构化注入 | 无 | Session Note 结构化注入 |
| 摘要模型 | 复用主对话 ModelProfile | 独立 Haiku | N/A | 独立便宜模型 |
| 全量 LLM 压缩 | 有 (Tier 2/3) | 有 (Auto-Compact) | 无 | **去除** |
| 压缩后恢复 | 工具+附件+派发 | 文件+技能+计划 | N/A | 文件+技能+计划 |
| Action vs Observation | 不区分 | 不区分 | 不区分 | **区分**，Action 优先 |

## 5. 新三层架构

### 5.1 总体架构

从第一性原理出发，Agent 对话生命周期需要回答四个问题：

```
Q1: ReAct Loop 进行中, context 快满了怎么办?
    → 即时裁剪 (纯结构化, 零 LLM, 快)

Q2: Run 结束后, 如何提取本次对话的关键信息?
    → 后台异步 LLM 提取 → Session Note

Q3: 新 Run 启动时, 如何给 agent 注入足够的上下文?
    → 加载 Session Note + 最近消息 + 同款裁剪

Q4: context 实在装不下了, 怎么收尾?
    → 软收尾 → 强制总结 (保留)
```

对应三层架构：

```
┌─────────────────────────────────────────────────────────────────┐
│                     Agent ReAct Loop                            │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │  Layer 1: 即时裁剪层 (compact_pipeline.py 重构)         │    │
│  │                                                          │    │
│  │  时机: 每次 model call 前                                │    │
│  │  方法: 纯结构化, 零 LLM                                   │    │
│  │  三阶段:                                                  │    │
│  │    ratio ≥ 0.75 → 轻度裁剪 (mask old observations)       │    │
│  │    ratio ≥ 0.88 → 重度折叠 (fold old turns)             │    │
│  │    ratio ≥ 0.93 → 软收尾 (soft inject, 不变)             │    │
│  │    ratio ≥ 0.95 → 强制总结 (force final, 不变)           │    │
│  │                                                          │    │
│  │  核心策略:                                                │    │
│  │    - 滑动窗口: 保留最近 K=3 轮完整 ReAct turn            │    │
│  │    - 窗口外 Observation → 通用 mask (保留 tool_name+args)│    │
│  │    - 窗口外 Discourse (user/assistant text) → 保留        │    │
│  │    - 窗口外 thinking → 丢弃                              │    │
│  │    - 白名单: code_explore / fs_read(outline) 完整保留    │    │
│  │    - Action (tool_call name+args) 始终保留               │    │
│  └──────────────────────────────────────────────────────────┘    │
│                              ↓ (Run 结束)                       │
└─────────────────────────────────────────────────────────────────┘
                               ↓
┌─────────────────────────────────────────────────────────────────┐
│  Layer 2: Session Note 层 (session_memory.py 重构)              │
│                                                          │
│  时机: Run 结束后, 后台 asyncio task                      │
│  方法: LLM 提取 (用便宜模型)                              │

│    - 首次: ≥ 2 个 tool turn 或 ≥ 3k tokens               │

│    - 自然断点检查 (无 unresolved tool_use)                │
│                                                          │
│  合并策略: 方案 C — LLM 全量输出 + 分 section 差异化       │
│    - LLM 看到完整已有 Note + 新增对话                     │
│    - 输出合并后的完整 Note                                │

│                                                          │

└───────────────────────────────────────────────────────────┘

│  Layer 3: 跨 Run 注入层 (conversation_context.py 重构)          │
│                                                          │

│  方法: 纯结构化, 零 LLM                                   │
│                                                          │
│  ★ Layer 1 裁剪不持久化 — DB 始终存完整消息             │
│  ★ Layer 3 从 DB 加载完整消息后独立做裁剪 (不重复)       │

│    2. 加载 T 之后的消息 (完整, 未裁剪)                   │

│                                                          │
│  ★ 不再有 ContextSummary (compaction) 概念               │

│  ★ 短对话跨 Run 不裁剪, 直接全文注入                      │
└───────────────────────────────────────────────────────────┘
```

### 5.2 Layer 间衔接逻辑

#### 5.2.1 Layer 1 → Layer 2：Run 结束触发

```
ReAct Loop 运行中 → Layer 1 在内存中裁剪 messages
  ↓ (裁剪结果只在内存, 不写回 DB)
Run 结束 → DB 存的是完整原始消息
  ↓
后台 asyncio task 触发 → Layer 2 从 DB 加载新消息 → LLM 提取 Session Note
```

**关键**：Layer 1 的裁剪是**临时性的**，只在当前 ReAct loop 的内存中生效。Run 结束后，DB 中存储的始终是**完整的、未裁剪的消息**。Layer 2 从 DB 加载新消息做提取时，看到的是完整数据。

#### 5.2.2 Layer 2 → Layer 3：跨 Run 注入

```
新 Run 启动 → Layer 3 调用 build_history_for()
  ↓
查 Session Note (covers_up_to = T)
  ↓
从 DB 加载 T 之后的完整消息 (未裁剪)
  ↓
计算 ratio → 按 ratio 分级注入 (见 §8.1)
```

**关键**：Layer 3 从 DB 加载的是**完整消息**，不是 Layer 1 裁剪过的。所以 Layer 3 的裁剪是**第一次也是唯一一次**对这些消息做裁剪，不存在"重复裁剪"问题。

#### 5.2.3 防止重复裁剪的设计

| 问题 | 设计决策 | 理由 |
|---|---|---|
| Layer 1 裁剪结果会持久化吗？ | **不持久化** | 只在 ReAct loop 内存中生效，Run 结束消失 |
| Layer 3 加载的消息是裁剪过的吗？ | **否，完整消息** | DB 始终存完整数据，Layer 3 独立做裁剪 |
| Layer 3 会重复 Layer 1 的裁剪吗？ | **不会** | Layer 1 的裁剪结果未持久化，Layer 3 面对的是全新完整数据 |
| 为什么不让 Layer 1 持久化裁剪结果？ | **避免丢信息 + 避免 ORM bug** | 持久化裁剪结果会永久丢失原始数据；旧架构 Tier 4 的 `expunge_all` 缺失 bug 就是因为意外持久化了裁剪结果 |

### 5.3 新旧架构对照

| 维度 | 旧架构 (四层) | 新架构 (三层) |
|---|---|---|
| 运行时裁剪 | Tier 0: 五阶段, 0.70/0.80/0.88/0.93/0.95 | Layer 1: 三阶段, 0.75/0.88/0.93/0.95 |
| 裁剪策略 | 29 个 per-tool summarizer 映射 | 通用 mask + 白名单 |
| 轮次保留 | K=2 | K=3 |
| Action vs Observation | 不区分 | Action 优先保留 |
| 会话级摘要 | Tier 1: 非结构化文本 | Layer 2: 10-section YAML |
| 全量 LLM 压缩 | Tier 2/3: 有 (compact_conversation) | **去除** |
| 跨 Run 序列化 | Tier 4: 独立裁剪逻辑 | Layer 3: 复用 Layer 1 逻辑 |
| 手动压缩 | 有 (/compact API) | **去除** |
| 裁剪逻辑统一 | Tier 0 和 Tier 4 各自实现 | Layer 1 和 Layer 3 统一 (CompactMessage) |

### 5.4 为什么去除 LLM 全量压缩层

Session Note 已经是 LLM 压缩的产物 — 只不过它不是"把历史压缩成一段话"，而是"从历史中提取结构化信息"。后者比前者信息密度高得多。

再在跨 Run 时做一次 LLM 全量压缩，等于：
1. 重复处理了 Session Note 已覆盖的 Discourse 内容
2. 额外花一次 LLM 调用（可能用昂贵模型）
3. 产出的摘要质量不一定比 Session Note 好（Session Note 是增量的，每次只处理新内容；全量压缩要一次性处理整段历史）

当 Layer 1 结构化裁剪到极限还不够时，soft wrap-up 和 force final 是正确的收尾路径 — 继续跑下去没有意义。

## 6. Layer 1: 即时裁剪层

### 6.1 信息价值排序

新架构的核心理念：**不是所有消息同等重要**。

```
信息价值排序 (高 → 低):

1. user 的最新消息           ← 必须完整保留
2. assistant 的 tool_call   ← Action: 做了什么决策、调了什么工具
   (name + args)               这是 agent 的"行为记录"，丢了就无法理解决策链
3. assistant 的文本回复      ← Discourse: 结论和推理
4. tool_result              ← Observation: 工具返回的数据
                               这是最大的体积来源 (>70%)，但可重新获取
5. thinking/reasoning       ← 推理过程，过了就没用了
```

### 6.2 阈值设计

```
0% ──────────── 0.75 ──────── 0.88 ──────── 0.93 ── 0.95 ── 100%
                 │              │              │       │
  正常运行       │              │              │       │
                 ↓              ↓              ↓       ↓
            轻度裁剪         重度折叠       软收尾   强制总结
            (mask)          (fold)         (soft)   (force)
```

| 阶段 | 阈值 | 200k 余量 | 操作 | 理由 |
|---|---|---|---|---|
| 轻度裁剪 | 0.75 | 50k | mask 窗口外 Observation；保留 Discourse | 50k 余量足够 10-15 轮工具调用；通用 mask 压缩率 98%，一次裁剪释放大量空间 |
| 重度折叠 | 0.88 | 24k | 折叠旧 turns → 单个 marker；截断旧 Discourse | 24k 余量只够 5-8 轮；旧上下文必须大量清除，但不直接跳 soft，给 agent 再试几轮的机会 |
| 软收尾 | 0.93 | 14k | 注入收尾指令，要求尽快给结论 | 14k 不够再做大工具调用了 |
| 强制总结 | 0.95 | 10k | 禁止工具，强制总结 | 10k 是最后的安全阀 |

**为什么是 0.75 而不是 0.70？**

通用 mask 的压缩率（98%）比 per-tool summarizer（84%）更高，一次裁剪释放的空间更大。首次触发可以更晚（0.75 vs 0.70），因为：
- 0.75 对应 200k 模型的 150k，50k 余量充足
- 过早（0.70 = 60k 余量）mask 掉旧 observation 后，agent 在 60k 余量内可能需要反复重读同一文件
- 不需要 Stage 2（再裁一次 observation 没意义，已经 mask 了），直接跳到 fold

**为什么去除 Stage 2？**

当前 Stage 2（0.80）是对 Stage 1 已裁剪的内容再裁剪更激进。但通用 mask 后，observation 已经被替换为 ~100 token 的 marker，Stage 2 没有东西可再裁。需要进一步压缩时直接 fold 整个旧 turn。

### 6.3 通用 Mask 策略

替代 29 个 per-tool summarizer 映射，使用一个通用 mask 函数 + 少量白名单。

#### Mask 格式

```text
[masked tool=fs_read path='backend/app/services/compact_pipeline.py' mode='full']
[recover: fs_read(path='backend/app/services/compact_pipeline.py', mode='full') 重新读取]
```

#### 白名单（完整保留）

| 工具 | 条件 | 理由 |
|---|---|---|
| `code_explore` | 所有 | 结果本身是高密度摘要，丢了可惜 |
| `fs_read` | mode=outline / mode=head | 已经是短摘要，不需要 mask |

#### Action 保留策略

```python
# assistant 消息中的 tool_calls 字段 (Action) 始终保留
# 只裁剪 tool 消息中的 content (Observation)

# 裁剪前:
{"role": "assistant", "content": "让我读取这个文件", "tool_calls": [{"function": {"name": "fs_read", "arguments": '{"path": "app.py"}'}}]}
{"role": "tool", "tool_call_id": "xxx", "content": "<5000 行文件内容>"}

# 裁剪后:
{"role": "assistant", "content": "让我读取这个文件", "tool_calls": [{"function": {"name": "fs_read", "arguments": '{"path": "app.py"}'}}]}
{"role": "tool", "tool_call_id": "xxx", "content": "[masked tool=fs_read path='app.py' mode='full']\n[recover: fs_read(path='app.py', mode='full') 重新读取]"}
```

#### Discourse 轻度截断策略（仅在 fold 阶段）

```python
# fold 阶段对旧 Discourse 的处理:
# user 消息: 保留完整（通常很短）
# assistant 文本: 保留首尾各 200 字符，中间用 [...] 替代
# thinking: 丢弃

# 例如:
# 裁剪前: "我分析了这个文件的结构，发现它包含三个主要模块：第一是 compact_pipeline，
#  包含 21 种 summarizer；第二是 context_compaction_service，包含三分支策略；
#  第三是 conversation_context，包含跨 Run 序列化逻辑。建议我们..."
# 裁剪后: "我分析了这个文件的结构，发现它包含三个主要模块：[...截断...]
#  建议我们..."
```

### 6.4 滑动窗口设计

```
保留最近 K=3 轮完整 ReAct turn (比当前 K=2 多一轮)

一轮 ReAct turn = assistant(tool_calls) + tool(tool_result) 对

K=3 的理由:
  - K=2 太少: agent 只能看到最近 2 轮的工具结果，前面读过的文件全丢了
  - K=3 给 agent 多一轮的缓冲: 最近 3 轮的 tool_result 完整保留
  - 200k 上下文下，3 轮通常 15-30k token，占比可控
```

### 6.5 统一数据结构

Layer 1（ReAct loop 内，dict 格式）和 Layer 3（跨 Run，ORM 格式）统一到 `CompactMessage`：

```python
@dataclass
class CompactMessage:
    """Unified message representation for Layer 1 and Layer 3."""
    id: str
    role: str  # "system" | "user" | "assistant" | "tool"
    content: str
    tool_calls: list[dict] | None = None  # assistant tool_calls (Action)
    tool_call_id: str | None = None  # tool message's call_id
    created_at: float = 0.0
    is_pinned: bool = False
```

Layer 1 和 Layer 3 各自只保留适配层（dict ↔ CompactMessage / ORM ↔ CompactMessage），核心裁剪逻辑统一到一套实现。

### 6.6 防止 Stage 反复横跳

#### 6.6.1 问题：什么叫"反复横跳"

ReAct loop 运行中，ratio 随着每轮工具调用不断变化。如果 ratio 在 0.75（mask 阈值）附近来回波动，会产生两个严重问题：

**问题 1：无意义重复裁剪**

```
轮次 3: ratio=0.76 → mask 裁剪 → ratio 降到 0.42
轮次 4-5: 新消息涌入 → ratio 升到 0.76
轮次 6: ratio=0.76 → 再次 mask

但 K=3 的滑动窗口意味着轮次 3-5 的消息都在保留窗口内
mask 实际上没东西可裁（old 区域是空的）
→ 执行了 mask 逻辑但 ratio 几乎没降
→ 被判定为"压缩失败"
```

**问题 2：断路器误触发**

当前代码中 `mark_compact_result` 的逻辑：连续 3 次"压缩失败"（ratio 没降 15%+）后 `compact_disabled = True`，**永久禁用压缩**。

```
轮次 3:  mask → 效果小 → compact_consecutive_failures = 1
轮次 6:  mask → 效果小 → compact_consecutive_failures = 2
轮次 9:  mask → 效果小 → compact_consecutive_failures = 3
→ compact_disabled = True!
→ 此后即使 ratio 到 0.90 也不裁剪了，直接 soft_inject → force_final
→ Agent 还有大量上下文空间，但被强制收尾了
```

#### 6.6.2 解决方案

引入两个新字段：

```python
@dataclass
class TerminationState:
    # ... existing fields ...
    last_compact_stage: int = 0       # 上次执行的裁剪阶段 (0=无, 1=mask, 3=fold)
    turns_since_compact: int = 0      # 距上次裁剪经过的轮次数
```

**三条防横跳规则**：

| 规则 | 条件 | 动作 | 理由 |
|---|---|---|---|
| 最小间隔 | mask 后 `turns_since_compact < K+1`（K=3 → 间隔 < 4 轮） | 跳过 mask | K=3 的滑动窗口意味着前 3 轮消息都在保留窗口内，mask 没东西可裁。间隔必须 > K 才有意义 |
| 直接升级 | mask 后 ratio 继续升到 ≥ 0.88 | 跳过 mask，直接 fold | mask 已把旧 observation 都 mask 了，再 mask 没意义。需要进一步压缩时直接 fold 整个旧 turn |
| fold 后不再压缩 | fold 后无论 ratio 多高 | 不再执行任何裁剪 | fold 是最重的结构化裁剪，fold 后如果 ratio 还在涨说明新消息涌入太快，再裁也没用。直接进入 soft_inject → force_final |

**为什么最小间隔是 K+1 而不是 3？**

```
K=3 滑动窗口保留最近 3 轮完整 ReAct turn

mask 在轮次 N 执行:
  → 裁剪了 N-3 之前的旧 observation
  → N-2, N-1, N 在保留窗口内 (完整)

轮次 N+1: 窗口变为 N-2, N-1, N, N+1 → old 区域 = N-3 之前 (已 mask 过)
轮次 N+2: 窗口变为 N-1, N, N+1, N+2 → old 区域 = N-3 之前 (已 mask 过)
轮次 N+3: 窗口变为 N, N+1, N+2, N+3 → old 区域 = N-3 之前 (已 mask 过)

→ N+1, N+2, N+3 时再次 mask 都没东西可裁 (old 区域没变)
→ 必须等到 N+4 才有新的消息进入 old 区域

所以最小间隔 = K + 1 = 4 轮
```

#### 6.6.3 实现代码

```python
def should_compact(state: TerminationState, ratio: float) -> str | None:
    """Decide if compaction should run this turn.

    Returns: "mask" | "fold" | None
    防横跳: 避免在 mask 阈值附近无意义重复裁剪
    """
    # 注: compact_disabled 已删除, 防横跳机制从根本上避免了误触发

    if ratio < 0.75:
        return None  # 不需要裁剪

    # 防横跳检查
    if state.last_compact_stage == 1:
        # 上次做了 mask
        if state.turns_since_compact < 4:
            # 间隔不够 (K+1=4)，old 区域没新消息可裁
            # 但如果 ratio 已经到 0.88+，直接跳 fold（升级而非重复）
            if ratio >= 0.88:
                return "fold"
            return None  # 跳过，等
        else:
            # 间隔够了
            if ratio >= 0.88:
                return "fold"  # 直接 fold，不重复 mask
            return "mask"  # 有新的 old 消息可裁

    if state.last_compact_stage == 3:
        # 上次做了 fold，不再压缩
        # fold 后如果 ratio 还在涨 → 直接 soft/force 收尾
        return None

    # 从未裁剪过
    if ratio >= 0.88:
        return "fold"
    return "mask"
```

> **调用方职责**：`should_compact` 只负责决策。调用方 (ReAct loop) 需要在每轮
> 工具调用后更新 `TerminationState`：
>
> ```python
> # 每轮工具调用后
> state.turns_since_compact += 1
>
> action = should_compact(state, ratio)
> if action:
>     if action == "mask":
>         messages = run_compact_pipeline_unified(messages, stage=1)
>         state.last_compact_stage = 1
>     elif action == "fold":
>         messages = run_compact_pipeline_unified(messages, stage=3)
>         state.last_compact_stage = 3
>     state.turns_since_compact = 0  # 重置计数
> ```
>
> `compact_disabled` 字段已删除。旧架构中 `compact_disabled` 的根本原因
> 是无意义重复 mask 导致"压缩失败"累积。防横跳机制从源头消除了这个问题。

#### 6.6.4 完整运行示例

```

轮次 2:  ratio=0.72  last=0  turns=0   → 不裁剪 (ratio < 0.75)
轮次 3:  ratio=0.76  last=0  turns=0   → ✅ mask
         → ratio 降到 0.42, last=1, turns=0

轮次 4:  ratio=0.48  last=1  turns=1   → 不裁剪 (ratio < 0.75)
轮次 5:  ratio=0.65  last=1  turns=2   → 不裁剪 (ratio < 0.75)
轮次 6:  ratio=0.76  last=1  turns=3   → 不裁剪 (turns < 4, ratio < 0.88)
轮次 7:  ratio=0.79  last=1  turns=4   → ✅ mask (turns >= 4, ratio >= 0.75)
         → ratio 降到 0.50, last=1, turns=0

轮次 8:  ratio=0.55  last=1  turns=1   → 不裁剪
轮次 9:  ratio=0.70  last=1  turns=2   → 不裁剪
轮次 10: ratio=0.76  last=1  turns=3   → 不裁剪 (turns < 4)
轮次 11: ratio=0.85  last=1  turns=4   → ✅ mask (turns >= 4, ratio >= 0.75)
         → 但 mask 效果有限 (old 区域不多)
         → ratio 只降到 0.78

轮次 12: ratio=0.82  last=1  turns=1   → 不裁剪 (turns < 4)
轮次 13: ratio=0.88  last=1  turns=2   → ✅ fold (ratio >= 0.88, 直接升级)
         → fold 折叠所有旧 turn
         → ratio 降到 0.30, last=3, turns=0

轮次 14: ratio=0.35  last=3  turns=1   → 不裁剪 (fold 后不再压缩)
轮次 15: ratio=0.60  last=3  turns=2   → 不裁剪 (fold 后不再压缩)
轮次 16: ratio=0.93  last=3  turns=3   → 不裁剪 (fold 后不再压缩, last_compact_stage==3)
         → 但 ratio >= 0.93 → soft_inject 触发
轮次 17: ratio=0.96  last=3  turns=4   → 不裁剪 (fold 后不再压缩)
         → ratio >= 0.95 → force_final 触发 (收尾)
```

> 注：soft_inject (ratio ≥ 0.93) 和 force_final (ratio ≥ 0.95) 不受防横跳限制，
> 它们是收尾机制而非裁剪机制，在 `should_compact` 返回 None 后由
> `react_loop_termination` 独立判断触发。

对比：没有防横跳时，轮次 6、9、10 都会触发无意义 mask，很快累积 3 次"失败"导致 `compact_disabled = True`。

### 6.7 Layer 1 与 Layer 3 裁剪逻辑统一

```python
# backend/app/services/compact_pipeline.py (重构)

def run_compact_pipeline_unified(
    messages: list[CompactMessage],
    stage: int,  # 1=mask, 3=fold
    pinned_ids: set[str] | None = None,
    note_whitelist: set[str] | None = None,
) -> list[CompactMessage]:
    """Unified pipeline for both Layer 1 and Layer 3.

    Layer 1: pinned_ids = None (no pinned concept in ReAct loop)
    Layer 3: pinned_ids = set of pinned message IDs
    """
    if stage == 1:
        return _stage1_mask_unified(messages, note_whitelist)
    if stage == 3:
        return _stage3_fold_unified(messages, pinned_ids=pinned_ids)
    raise ValueError(f"unknown compact stage: {stage}")


def _stage1_mask_unified(
    messages: list[CompactMessage],
    note_whitelist: set[str] | None = None,
) -> list[CompactMessage]:
    """Stage 1: mask old observations, keep recent turns intact."""
    recent, old = _keep_recent_turns(messages, k=3)
    if not old:
        return list(messages)

    for msg in old:
        if msg.role != "tool":
            continue
        pair = _find_tool_call_for_tool_message(messages, msg)
        if pair is None:
            continue
        tool_name, args = pair

        # 白名单: 完整保留
        if _is_whitelisted(tool_name, args):
            continue

        # Session Note 白名单: 文件在 note.files_touched 中
        if note_whitelist:
            path = args.get("path", args.get("file", ""))
            if path and path in note_whitelist:
                continue

        # 通用 mask (就地修改 old 中的消息)
        msg.content = _build_mask_marker(tool_name, args)

    # 返回: 裁剪后的 old + 完整 recent (old 中已包含 system 消息)
    return old + recent


def _stage3_fold_unified(
    messages: list[CompactMessage],
    pinned_ids: set[str] | None = None,
) -> list[CompactMessage]:
    """Stage 3: fold old turns into a single marker."""
    system_msgs = [m for m in messages if m.role == "system"]
    recent, old = _keep_recent_turns(messages, k=3)
    if len(old) < FOLD_TURN_THRESHOLD:
        return list(messages)

    # 保护 pinned 消息
    pinned = [m for m in old if m.is_pinned or (pinned_ids and m.id in pinned_ids)]
    foldable = [m for m in old if not (m.is_pinned or (pinned_ids and m.id in pinned_ids))]

    if not foldable:
        return list(messages)

    fold_marker = _build_fold_marker(foldable)
    return system_msgs + [fold_marker] + pinned + recent


def _build_mask_marker(tool_name: str, args: dict) -> str:
    """Build a generic mask marker for a tool result."""
    path = args.get("path", args.get("file", args.get("pattern", "")))
    mode = args.get("mode", "")
    path_part = f" path='{path}'" if path else ""
    mode_part = f" mode='{mode}'" if mode else ""
    return (
        f"[masked tool={tool_name}{path_part}{mode_part}]\n"
        f"[recover: {tool_name}({', '.join(f'{k}={v!r}' for k, v in args.items())}) 重新获取]"
    )
```

```python
async def extract_session_note(
    conversation_id: str,
    existing_note: SessionNote | None,
    generate_fn: Callable,
) -> SessionNote | None:
    """Extract/update session note via LLM.

    Flow:
    1. Load new messages since last extraction (or all if first time)
    2. Check natural breakpoint (no unresolved tool_use)
    3. Build prompt: existing_note_yaml + new_messages_transcript
    4. LLM generates merged YAML
    5. Parse YAML → SessionNote
    6. Post-processing: enforce section limits, dedup
    """
    # 1. Load new messages
    last_covered = existing_note.covers_up_to if existing_note else None
    new_messages = await _load_messages_since(conversation_id, last_covered)
    if not new_messages:
        return existing_note

    # 2. Natural breakpoint check
    if not _at_natural_breakpoint(new_messages):
        return existing_note  # wait for a better breakpoint

    # 3. Build prompt
    existing_yaml = existing_note.to_yaml() if existing_note else "# (new note)"
    transcript = _render_transcript(new_messages)
    user_msg = f"# 已有笔记\n\n{existing_yaml}\n\n# 新增对话\n\n{transcript}"

    # 4. LLM generate (同步调用通过 executor 执行, 避免阻塞事件循环)
    loop = asyncio.get_event_loop()
    raw = await loop.run_in_executor(None, generate_fn, SYSTEM_PROMPT, user_msg)
    if not raw:
        return existing_note  # LLM failed, keep existing

    # 5. Parse
    note = SessionNote.from_yaml(raw)
    if note is None:
        # YAML parse failed, fallback to existing
        return existing_note

    # 6. Post-processing
    note = _enforce_section_limits(note)
    note.covers_up_to = _last_message_timestamp(new_messages)

    return note


def _enforce_section_limits(note: SessionNote) -> SessionNote:
    """Enforce section size limits to prevent unbounded growth."""
    note.key_decisions = _trim_list(note.key_decisions, max_items=20)
    note.files_touched = _trim_list(note.files_touched, max_items=30)
    note.commands_run = _trim_list(note.commands_run, max_items=20)
    note.artifacts_produced = _trim_list(note.artifacts_produced, max_items=10)
    note.blockers = _trim_list(note.blockers, max_items=10)
    note.open_questions = _trim_list(note.open_questions, max_items=10)

    # Total YAML size check
    yaml_str = note.to_yaml()
    if len(yaml_str) > 3000:
        # Compress: merge similar items, remove old resolved items
        note = _compress_note(note)

    return note

### 7.8 Note 压缩策略

```python
def _compress_note(note: SessionNote) -> SessionNote:
    """Compress session note when it exceeds size limit.

    Strategy:
    - key_decisions: merge similar items (e.g., "改了 A 文件" + "改了 B 文件" → "改了 A, B 等 N 个文件")
    - files_touched: remove old "已读" entries, keep "已改" entries
    - commands_run: remove old entries, keep only recent 10
    - blockers/open_questions: remove [已解决]/[已回答] entries older than 5 items ago
    """
    # Merge similar decisions
    note.key_decisions = _merge_similar_decisions(note.key_decisions)

    # Trim files: keep all "已改", trim "已读" to recent 15
    changed = [f for f in note.files_touched if "已改" in f]
    read_only = [f for f in note.files_touched if "已读" in f]
    note.files_touched = changed + read_only[-15:]

    # Trim commands
    note.commands_run = note.commands_run[-10:]

    # Remove old resolved items: keep all unresolved + recent 5 resolved
    note.blockers = [
        b for i, b in enumerate(note.blockers)
        if "[已解决]" not in b or i >= len(note.blockers) - 5
    ]
    note.open_questions = [
        q for i, q in enumerate(note.open_questions)
        if "[已回答]" not in q or i >= len(note.open_questions) - 5
    ]

    return note
```

## 8. Layer 3: 跨 Run 注入层

### 8.1 分级注入策略

Layer 3 不是任何时候都注入 Session Note 和裁剪。而是根据 ratio 分级处理：

```
新 Run 启动 → build_history_for()
  │
  ├─ 查 Session Note → covers_up_to = T
  ├─ 从 DB 加载 T 之后的完整消息 (未裁剪)
  ├─ 合并 pinned 消息
  ├─ expunge_all() (脱离 ORM session)
  ├─ 转换为 CompactMessage
  ├─ 计算 ratio = (消息 token + prompt token) / 200k
  │
  ├─ 情况 A: T 之后无消息
  │    ├─ A1: 有 Session Note → 只注入 Note
  │    └─ A2: 无 Session Note → 首次对话/提取失败，返回空历史
  │
  ├─ 情况 B: ratio < 0.50 (上下文充足)
  │    → 只注入全文消息, 不注入 Note
  │    → Agent 能看到所有原始消息, 比看摘要更好
  │
  ├─ 情况 C: 0.50 ≤ ratio < 0.75 (中等长度)
  │    → 注入 Session Note + 全文消息
  │    → Note 作为 "提前预告", Agent 知道整体上下文
  │    → 不裁剪 (还不需要)
  │
  ├─ 情况 D: 0.75 ≤ ratio < 0.88 (需要轻裁剪)
  │    → 注入 Session Note + mask 裁剪后的消息
  │    → mask 窗口外 Observation, 保留 Discourse
  │
  ├─ 情况 E: ratio ≥ 0.88 (需要重裁剪)
  │    → 注入 Session Note + fold 裁剪后的消息
  │    → 折叠旧 turns → 单个 marker
  │
  └─ Token budget 超限兜底: 从最旧 non-pinned 开始丢弃
```

**为什么 0.50 才开始注入 Note？**

- ratio < 0.50 意味着消息总量不到上下文的 50%，Agent 能直接看到所有原始消息。此时注入 Session Note 反而浪费 token（Note 可能 1000-3000 token）且信息密度低于原始消息。
- 0.50 是一个合理的分界点：低于此值全文注入最好；高于此值 Note 的摘要价值开始超过它的 token 成本。

**为什么不直接从 0.75 开始才注入 Note？**

- 0.50-0.75 区间虽然不需要裁剪，但消息量已经不小（50%-75% 上下文）。此时注入 Note 作为"地图"，让 Agent 在阅读全文前先了解整体状态，有助于更好地理解上下文。
- Note 的 token 成本通常 1000-3000，在 50% 上下文时注入只占 0.5%-1.5%，成本极低。

) -> list[dict]:
    """Build chat history for a new Run.

    分级注入策略:
    - 查 Session Note → covers_up_to = T
    - 加载 T 之后的完整消息 (DB 存的是未裁剪的原始数据)
    - 按 ratio 分级注入 (见 §8.1)
    """
    # 1. 查 Session Note
    session_note = await _get_session_note(conversation_id)

    # 2. 加载 Note covers_up_to 之后的完整消息
    since_ts = session_note.covers_up_to if session_note else None
    messages = await _load_messages_since(conversation_id, since_ts)

    # 3. 合并 pinned 消息
    pinned = await _get_pinned_messages(conversation_id)
    all_messages = _merge_pinned(messages, pinned)

    # 4. CRITICAL: expunge_all before any compaction
    #    DB 始终存完整消息, Layer 1 裁剪不持久化
    #    Layer 3 从 DB 加载的是完整数据, 独立做裁剪
    db.expunge_all()

    # 5. 转换为 CompactMessage
    compact_msgs = to_compact_messages_orm(all_messages)

    # 6. 计算 ratio
    prompt_estimate = _estimate_prompt_tokens(options)
    loaded_tokens = _estimate_compact_messages_tokens(compact_msgs)
    ratio = (loaded_tokens + prompt_estimate) / 200_000  # fixed 200k

    # 7. 分级注入决策
    inject_note = False
    apply_compaction = False
    compact_stage = 0  # 0=none, 1=mask, 3=fold

    if not compact_msgs:
        # 情况 A: Note 之后无消息
        # 子情况 A1: 有 Session Note → 只注入 Note
        # 子情况 A2: 无 Session Note → 首次对话或 Note 提取失败，返回空历史
        inject_note = session_note is not None
    elif ratio < 0.50:
        # 情况 B: 上下文充足, 只注入全文
        inject_note = False
    elif ratio < 0.75:
        # 情况 C: 中等长度, Note + 全文 (不裁剪)
        inject_note = True
    elif ratio < 0.88:
        # 情况 D: 需要轻裁剪, Note + mask
        inject_note = True
        apply_compaction = True
        compact_stage = 1
    else:
        # 情况 E: 需要重裁剪, Note + fold
        inject_note = True
        apply_compaction = True
        compact_stage = 3

    # 8. 执行裁剪 (如果需要)
    if apply_compaction:
        note_whitelist = _extract_whitelist(session_note) if inject_note else None
        compact_msgs = run_compact_pipeline_unified(
            compact_msgs,
            stage=compact_stage,
            pinned_ids=_pinned_ids(pinned),
            note_whitelist=note_whitelist,
        )

    # 9. 转换回 dict 格式
    result = from_compact_messages(compact_msgs)

    # 10. Token budget 兜底裁剪
    result = _trim_to_budget(result, prompt_estimate, budget=200_000)

    # 11. 注入 Session Note (如果需要)
    if inject_note and session_note:
        note_xml = session_note.to_xml()
        result = _inject_session_note(result, note_xml)

    return result
```

### 8.3 Session Note 白名单注入

```python
def _extract_whitelist(note: SessionNote | None) -> set[str] | None:
    """Extract file paths from Session Note's files_touched.

    These files are preserved longer in Layer 1 compaction.
    """
    if not note or not note.files_touched:
        return None

    whitelist = set()
    for entry in note.files_touched:
        # entry format: "path/to/file.py (已读, 292 行)"
        # extract the path part
        path = entry.split("(")[0].strip()
        if path:
            whitelist.add(path)
    return whitelist
```

# backend/app/services/conversation_context.py (扩展)

async def _build_capability_context(
    conversation_id: str, agent_ids: list[str]
) -> str:
    """Build a capability context block for post-compaction restoration.

    Collects:
    - Current tool names
    - Active attachments
    - Active dispatch plan
    - Recent file paths (NEW: from Session Note files_touched)
    - Active plan cards (NEW: from create_plan tool results)
    - Recent skill loads (NEW: from load_skill tool results)
    """
    parts: list[str] = ["[能力上下文]"]

    # ... existing: tools, attachments, dispatch plan ...

    # NEW: Recent file paths from Session Note
    session_note = await get_session_note(conversation_id)
    if session_note and session_note.files_touched:
        files_list = ", ".join(session_note.files_touched[:10])
        parts.append(f"- 最近操作文件: {files_list}")

    # NEW: Active plan cards
    try:
        async with get_local_db() as db:
            plan_msgs = (
                (await db.execute(
                    select(Message).where(
                        and_(
                            Message.conversation_id == conversation_id,
                            Message.status == "complete",
                        )
                    ).order_by(desc(Message.created_at)).limit(50)
                )).scalars().all()
            )
            active_plans = []
            for msg in plan_msgs:
                for p in msg.parts_list:
                    if p.get("type") == "tool_result":
                        data = _try_parse_json(_extract_tool_result_text(p))
                        if data and data.get("planId"):
                            active_plans.append(f"planId={data['planId']}")
            if active_plans:
                parts.append(f"- 活跃计划: {', '.join(active_plans[:3])}")
    except Exception:
        pass

    # NEW: Recent skill loads
    try:
        async with get_local_db() as db:
            skill_msgs = (
                (await db.execute(
                    select(Message).where(
                        and_(
                            Message.conversation_id == conversation_id,
                            Message.status == "complete",
                        )
                    ).order_by(desc(Message.created_at)).limit(50)
                )).scalars().all()
            )
            skills = set()
            for msg in skill_msgs:
                for p in msg.parts_list:
                    if p.get("type") == "tool_use" and p.get("toolName") == "load_skill":
                        slug = (p.get("args") or {}).get("slug", "")
                        if slug:
                            skills.add(slug)
            if skills:
                parts.append(f"- 已加载技能: {', '.join(sorted(skills))}")
    except Exception:
        pass

    if len(parts) == 1:
        return ""
    return "\n".join(parts)

## 12. 风险与降级

### 12.1 风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| YAML 解析失败 | 中 | 低 | Fallback 到纯文本注入 |
| 摘要模型不可达 | 低 | 中 | 回退到主对话 ModelProfile |
| 通用 mask 丢失关键信息 | 中 | 中 | 白名单 + recover hint + Session Note 兜底 |
| CompactMessage 转换丢信息 | 中 | 高 | 充分测试 + 渐进式迁移 + feature flag |
| 方案 C 合并语义错误 | 低 | 中 | 分 section 差异化策略 + _enforce_section_limits 后处理 |
| Note 无限增长 | 低 | 低 | _enforce_section_limits + _compress_note |
| 前端编辑竞态 | 低 | 低 | optimistic concurrency + version |

### 12.2 降级策略

```
Session Note 不可用时:
  → Layer 3 跳过 Note 注入，直接加载全部历史消息
  → Layer 1 裁剪仍正常工作 (无白名单，全量 mask)
  → Agent 仍能正常对话，只是跨 Run 上下文较差

摘要模型不可用时:
  → Session Note 不更新 (保留上一次的 Note)
  → Layer 1/3 裁剪不受影响 (纯结构化，不依赖 LLM)
  → 回退到主对话 ModelProfile 做提取 (可选)

Layer 1 通用 mask 裁剪异常时:
  → feature flag 切换回旧的 per-tool summarizer (Phase 3 保留)
  → 或跳过裁剪，直接进入 soft_inject / force_final

CompactMessage 转换异常时:
  → 回退到原有独立实现 (保留旧代码作为 fallback)
  → 通过 feature flag 控制

方案 C LLM 输出格式错误时:
  → YAML 解析失败 → 保留已有 Note 不更新
  → 下次提取时重试
  → 连续 3 次失败 → 停止提取，使用已有 Note
```

     (BREAKER_DUP)      (BREAKER_ERR)     compact_disabled
            │                 │           (防横跳机制 §6.6
            │                 │            从根本上消除了
            └────────┬────────┘            误触发根因)
                     ↓
              force_after_* = True
                     │
                     ↓
                force_final
                (FORCED_FINAL)
                     │
                     ↓
              forced_done = True
              → hard_stop
```

> **变更说明**：新架构中 `compact_consecutive_failures` 和 `compact_disabled` 已删除。
> 旧架构中 `compact_disabled` 的根本原因是 mask 在滑动窗口内没东西可裁，
> 被误判为"压缩失败"并累积 3 次后永久禁用。防横跳机制 (§6.6) 通过最小间隔
> 规则从源头杜绝了这种无意义重复裁剪，因此 `compact_disabled` 路径不再需要。
>
> 保留的断路器：`BREAKER_DUP`（重复工具调用）和 `BREAKER_ERR`（工具连续失败）
> 仍独立于压缩机制运行，触发后直接 soft_inject → force_final。

### 附录 E: Token 估算说明

当前 token 估算排除了 JSON 结构开销（`role`、`tool_call_id`、`type` 等字段名），实际 token 消耗比估算值高 15-25%。

这意味着：
- 0.75 的 mask 阈值在实际使用中对应约 0.60-0.65 的真实 context 占用率
- 0.88 的 fold 阈值对应约 0.72-0.76 的真实占用率
- 这给了额外的安全缓冲

**后续优化**：可以在 `estimate_dict_message_tokens` 中增加 JSON 结构开销的估算（每条消息额外 +8-12 token），使阈值更精确。但当前阈值已有足够缓冲，不急。

### 附录 F: 方案 C 合并策略详解

#### 为什么不选方案 A（局部追加）

方案 A 让 LLM 只提取新增内容，代码层面追加到已有 Note。问题是：

```
已有 Note:
  key_decisions:
    - "[14:32] 使用 PostgreSQL 作为主库"

新增对话:
  用户: "改主意了，用 SQLite 吧"
  agent: "好的，切换到 SQLite"

方案 A 输出 (LLM 看不到已有 Note):
  key_decisions:
    - "[15:00] 使用 SQLite 作为主库"

代码层面追加后:
  key_decisions:
    - "[14:32] 使用 PostgreSQL 作为主库"  ← 矛盾！
    - "[15:00] 使用 SQLite 作为主库"       ← 两个决策都在
```

LLM 看不到已有 Note，无法知道旧决策被推翻了。

#### 为什么不选方案 B（纯全量重写）

方案 B 让 LLM 看到已有 Note + 新增对话，输出合并后的完整 Note。这解决了矛盾问题，但：

1. 每次 token 开销大（已有 Note 可能 2000+ token + 新增对话 5000+ token）
2. LLM 可能丢失已有 Note 中的细节（重写时遗漏）
3. 没有差异化处理 — `next_steps` 应该覆盖但 `key_decisions` 应该追加

#### 方案 C 的优势

方案 C 结合了 A 和 B 的优点：

1. LLM 看到完整已有 Note + 新增对话 → 能处理矛盾
2. Prompt 中明确分 section 的处理规则 → 差异化
3. 代码后处理 `_enforce_section_limits` → 防止无限增长
4. `_compress_note` → 超 3000 token 时压缩

```
方案 C 的分 section 差异化:

title:              覆盖 (最新主题)
current_state:      覆盖 (最新状态)
key_decisions:      追加 + 去重 + 标记 [已更新]
files_touched:      追加 + 去重 (同一文件只保留最新状态)
commands_run:       追加 + 去重
artifacts_produced: 追加 + 去重
blockers:           追加 + 标记 [已解决]
open_questions:     追加 + 标记 [已回答]
next_steps:         覆盖 (已完成的不保留)
architecture_understanding: 覆盖 (合并补充)
```
